To upgrade ReputeCast, you replace the image or binary with a newer release and let it apply its database migrations;
everything else (configuration, secret key, data) stays as it is.

## See which version you run

An [instance admin](/reference/glossary/#instance-admin) sees the installed version, the latest release and its
changelog under <UiPath path="shell.userMenuInstanceAdmin > admin.instance" />, in the
<UiPath path="admin.versionCard" /> card. From the command line, `reputecast version` prints the same:
`reputecast <version> (<commit>) <Go version>`.

<Screenshot
  id="instance-settings"
  alt="The Version & updates card: installed version, the latest release v1.3.0 marked Up to date with its changelog link, What's new in v1.3.0, the upgrade command with a reminder to back up PostgreSQL first, and the daily release check switched on."
/>

- The badge <UiPath path="admin.updateAvailable" /> appears when the latest release is newer than the installed
  version. Builds without a release version number (such as `dev`) never show it.
- Under <UiPath path="admin.upgradeOnServer" />, the card shows the Docker Compose command
  `cd /opt/reputecast && docker compose pull && docker compose up -d`. Replace `/opt/reputecast` with the folder that
  holds your `docker-compose.yml`.
- The switch <UiPath path="admin.updateCheck" /> fetches the latest release from `api.github.com` once a day. The
  request carries no version number and no instance ID; it is the only outbound call ReputeCast makes on its own.
  Switch it off here, or set `updates.check: false` in the [configuration](/reference/configuration/) to turn it off
  for the whole instance (the switch is then locked).

## Before you begin

- Read the [release notes](/reference/release-notes/) of every version between yours and the new one, also on the
  [GitHub releases page](https://github.com/hostrepute/reputecast/releases).
- [Back up the database and the secret key](/self-hosting/backups/). Migrations change the schema, and a backup is the
  reliable way back.
- Plan a short interruption while the app restarts. On stop (`SIGTERM`, a redeploy), a worker fetches no new job and
  gives running jobs 10 seconds to finish; a send stops between batches, with the batch in flight sent and recorded.

## Upgrade

<Tabs syncKey="install">
<TabItem label="Docker Compose">

<Steps>

1. Go to the folder with your `docker-compose.yml` and take a backup:

   ```sh
   docker compose exec -T postgres pg_dump -U reputecast -d reputecast -Fc > reputecast-before-upgrade.dump
   ```

2. If you pin a version in `.env` (`REPUTECAST_VERSION=v1.4.2`), change it to the new release tag. Image tags are the
   release tags with their leading `v`, plus `latest`. Without `REPUTECAST_VERSION`, the compose file uses `latest`.

3. Pull the new image and recreate the app container:

   ```sh
   docker compose pull && docker compose up -d
   ```

   The image starts with `serve --auto-migrate`, so it applies pending migrations before it serves requests. The logs
   show one `migration applied` line per migration, and `docker compose ps` shows `app` as `healthy` once it is ready.

</Steps>

</TabItem>
<TabItem label="Binary">

<Steps>

1. Take a backup (see [back up and restore](/self-hosting/backups/)).

2. Download the archive for your platform and `checksums.txt` from the
   [release page](https://github.com/hostrepute/reputecast/releases), and check the download:

   ```sh
   sha256sum --ignore-missing -c checksums.txt
   ```

3. Stop every ReputeCast process, for example `sudo systemctl stop reputecast`.

4. Replace the binary (for example `/usr/local/bin/reputecast`) with the new one.

5. Apply the migrations once, with the same environment the service uses:

   ```sh
   reputecast migrate up
   ```

   It applies ReputeCast's migrations, then those of the job queue, and ends with `Database is up to date.`

6. Start every process again. If you run [several roles](/self-hosting/scaling/), upgrade all of them to the same
   version.

</Steps>

</TabItem>
</Tabs>

## While migrations are pending

A process whose database is missing migrations it needs, such as a binary replaced before `reputecast migrate up`
ran, doesn't write to it:

- Pages and the API read as usual. The app shows the <UiPath path="shell.bannerMaintenance" /> banner before any edit.
- Writes answer `503` with the code `maintenance`. Signing in and out still works, and sending providers' webhooks are
  still stored.
- Workers wait, so nothing is sent.
- `/readyz` answers `503`, so a load balancer or orchestrator keeps sending traffic to the previous release.

The process looks again every 5 seconds and carries on by itself once `reputecast migrate up`, or another process's
`--auto-migrate`, has applied them. Browser tabs left open across an upgrade offer <UiPath path="shell.bannerReload" />
to load the new version.

Migrations hold a lock in PostgreSQL: when several processes start with `--auto-migrate`, one applies them while the
others wait for it (up to 15 minutes), so each migration runs once. Run them over a direct or session-mode connection,
not through PgBouncer in transaction mode.

## Upgrade to 1.3.0

Version 1.3.0 changes these things on the server; the [release notes](/reference/release-notes/#130) list the rest.

- **23 new migrations** (`03360` to `03388`); some build indexes concurrently. One creates the `pg_trgm` extension for
  contact search, which the database's owner may create ([PostgreSQL](/self-hosting/postgres/#managed-postgresql)).
- **`delivery_events` becomes monthly partitions.** After the migrations, `migrate up` and `serve --auto-migrate`
  convert the table of every send, delivery, bounce, open and click, unless `reputecast migrate partition-events`
  already did. Nothing is copied and writes go on, but two steps read the whole table: on a very large table, run
  `reputecast migrate partition-events` yourself first, at a quiet hour
  ([monthly partitions](/self-hosting/postgres/#monthly-partitions-of-delivery_events)).
- **Read-only until migrated, and locked migrations**, as described [above](#while-migrations-are-pending).
- **`/metrics` moved** to its own listener, `:9464`. If Prometheus scraped the main port, point it at 9464 or set
  `metrics.token` ([health checks, metrics and logs](/self-hosting/monitoring/)).
- **A container health check.** The image runs `reputecast healthcheck`, so Docker reports the app as `healthy` once
  `/readyz` answers.
- **Rate limits per browser session.** Each signed-in browser has its own 600 requests a minute; the browsers behind
  one address share 6,000 ([security and hardening](/self-hosting/security/)).
- **nginx with HTTP/2.** The [nginx example](/self-hosting/reverse-proxy/) now turns HTTP/2 on, which loads the app
  much faster on phones.

## Upgrade to 1.2.0

Version 1.2.0 changes these things on the server; the [release notes](/reference/release-notes/#120) list the rest.

- **45 new migrations** (`03000` to `03350`) run on the first start, or with `reputecast migrate up`. Three indexes on
  the `contacts` and `messages` tables are built concurrently, so imports, sign-ups and sends keep going while they
  build on a large database.
- **One name for the public URL.** `REPUTECAST_PUBLIC_URL` now sets `http.public_url` for every way of running
  ReputeCast, the binary included, and the shipped `docker-compose.yml` passes it to the app as it is.
  `REPUTECAST_HTTP__PUBLIC_URL`, its earlier name, still works when `REPUTECAST_PUBLIC_URL` isn't set.
- **DNS lookups for mailbox providers.** ReputeCast finds a contact's mailbox provider from its domain's MX records,
  so Google Workspace counts as Gmail and Microsoft 365 as Outlook. After the upgrade, a background sweep every 2
  minutes looks up the company domains of existing contacts. The server needs a working resolver: the system's, or
  the servers in `dns.servers` ([configuration reference](/reference/configuration/)). A domain that hasn't been
  looked up yet counts as Other.
- **Shared report links expire.** Read-only report links made before 1.2.0 never expired; each one that still works
  now expires 30 days after the upgrade.
- **Default reply rules.** Workspaces that have no reply rule of their own get the default mailbox provider reply
  rules under <UiPath path="nav.providers > providers.tabTraffic" /> (see [traffic rules](/providers/traffic-rules/)).

## Check that it worked

- <UiPath path="admin.versionCard" /> shows the new version as installed.
- `reputecast migrate status` lists every migration with an applied date and none as `pending`. In Docker:
  `docker compose exec app /usr/local/bin/reputecast migrate status`.
- `/readyz` answers `ready` ([health checks, metrics and logs](/self-hosting/monitoring/)), and `reputecast doctor`
  reports the schema as `current`.

## Roll back

Going back to the previous image or binary does not undo migrations: the database keeps the newer schema. Within a
minor release (1.3.0 to 1.3.2) migrations only add, and across one minor release (1.3 to 1.2) the older binary runs on
the newer schema. Read the release notes first: a release that drops or renames something says so. Further back,
restore the backup.

- **Restore the backup** for an exact return to the state before the upgrade: stop ReputeCast, restore the dump you
  took (see [restore](/self-hosting/backups/#restore)), then start the version you ran before. Changes made after the
  upgrade are lost.
- **Pin the previous version** (`REPUTECAST_VERSION` in `.env`, then `docker compose up -d`), as the
  <UiPath path="admin.versionCard" /> card suggests, when you want to keep the data written since the upgrade. 1.2
  works on the partitioned `delivery_events` as well.
- `reputecast migrate down` rolls back only the latest ReputeCast migration, one per run, and leaves the job queue's
  tables alone. It is meant for development: down migrations drop data, so don't run it on a production database.

## Troubleshooting

- **The new container exits at start**: read `docker compose logs app`. A failed migration stops the start with
  `migrate: …`; restore the backup and report the error with the release version.
- **The app stays unhealthy and `/readyz` answers `database schema behind this release`**: no process applied the
  migrations. Run `reputecast migrate up`, or start one process with `--auto-migrate`.
- **`migrate: another migrator held the lock for 15m0s`**: another process was still migrating, for example converting
  a large `delivery_events`. Let it finish, then start this one again.
- **The version card says the update check failed**: the server can't reach `api.github.com`, or GitHub answered with an
  error. Nothing else is affected; the next check runs the following day.
- **The latest release shows a dash**: the check is off, or has not run yet.
