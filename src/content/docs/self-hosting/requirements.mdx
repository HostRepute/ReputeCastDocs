These are the ReputeCast system requirements: what a server needs to run one [instance](/reference/glossary/#instance) with the binary or the Docker image.

## Hardware

One server that runs ReputeCast and PostgreSQL together, with an SSD:

| Audience                         | vCPU | Memory | Disk  |
| -------------------------------- | ---- | ------ | ----- |
| Up to 250,000 contacts (minimum) | 2    | 2 GB   | 20 GB |
| Up to 1,000,000 contacts         | 4    | 4 GB   | 40 GB |

- **Memory.** At their busiest, ReputeCast used 300–380 MB and PostgreSQL about 500 MB (the Compose file's default
  settings), whatever the audience size; the rest of the memory caches the database. 1 GB is too little: ReputeCast,
  PostgreSQL and Docker together reached 0.86 GB, which leaves nothing for the operating system. A million contacts on
  2 GB with a cloud disk failed: searches and the send API slowed down (95% of sends within 3.9 s instead of 300 ms)
  and `/readyz` timed out, so a health check could have restarted the app.
- **CPU.** One vCPU served the contacts list and segment counts, but a burst of transactional email (rising to 200 a
  second) answered slower than the 300 ms target.
- **Disk.** The test database took 0.7 GB at 100,000 contacts, 1.4 GB at 300,000 and 3.8 GB at 1,050,000, with about
  two messages and three delivery events per contact. PostgreSQL's write-ahead log adds up to 1 GB, and the two
  images 0.5 GB. The sizes above leave room for a [backup](/self-hosting/backups/) and growth. The database grows with
  every message you send, for as long as [data is kept](/reference/limits-and-defaults/).
- **After a large import.** The first start's background jobs (engagement tiers, growth attribution, mailbox providers)
  took about 7 minutes for a million contacts on 4 vCPU and 4 GB with a cloud disk.
- **Beyond a million contacts** wasn't measured. [Split the roles](/self-hosting/scaling/),
  [tune PostgreSQL's memory](/self-hosting/postgres/#tune-memory-for-larger-audiences) and measure your own load.

### How these numbers were measured

Measured in November 2026 on ReputeCast 1.4.0 with the shipped Compose file and PostgreSQL 18. Each server was a
container with a CPU and memory limit, no swap and a disk capped at 3,000 IOPS and 125 MB/s, like a standard cloud
volume. It held the load test data: the demo workspace plus 50,000, 250,000 or 1,000,000 contacts with their messages
and events. The upstream load tests ran from outside it: ten people paging and searching contacts without a pause,
four people counting segments, and the send API rising to 200 messages a second.

A size passed when every target held, with no restart and no out-of-memory kill: contacts pages under 200 ms, search
under 150 ms, segment counts under 2 s and sends under 300 ms at the 95th percentile, and under 1% errors. The test
machine's cores are about 1.5 times as fast as a cloud vCPU (the first engagement-tier run of a million contacts took
200 s on four of them, 317 s on upstream's 4-vCPU GitHub runner), so each size was checked with its CPU time cut to
match. Results on a 4-vCPU runner are in
[scale with web, ingest and worker roles](/self-hosting/scaling/#measured-performance).

## Software

| Component       | Requirement                                                                                                                                                                                                                                                  |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Binary          | Linux, macOS or Windows on `amd64` or `arm64`. One static file (built without cgo) that contains the web app and the database migrations. Releases ship it as `.tar.gz` (`.zip` for Windows) with `checksums.txt`.                                           |
| Container image | `ghcr.io/hostrepute/reputecast` for `linux/amd64` and `linux/arm64`. Built on `gcr.io/distroless/static-debian13:nonroot`: no shell, runs as user `nonroot` (uid 65532), listens on port 8080, keeps its data in the volume `/var/lib/reputecast` and declares a health check that runs `reputecast healthcheck`. |
| Database        | PostgreSQL 16, 17 or 18. ReputeCast's tests run against all three; the shipped Compose file uses PostgreSQL 18. The migrations create one extension, `pg_trgm`, which comes with PostgreSQL ([PostgreSQL](/self-hosting/postgres/#managed-postgresql)). Background jobs queue in PostgreSQL, so no other service is required. |
| Runtime         | Nothing else. Node.js and Go are only needed to [build ReputeCast from source](/developers/contributing/).                                                                                                                                                   |

## Network

| Direction | What                                                                                                                                                                                                                                               |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Inbound   | A public HTTPS address (`http.public_url`) that sending providers can reach: they deliver events to `<public URL>/hooks/…`, and Zapier and Make call the same address. Terminate TLS in a [reverse proxy](/self-hosting/reverse-proxy/).          |
| Inbound   | Port 8080 (`http.addr`) from the reverse proxy only. Port 9464 (`metrics.addr`) from Prometheus only, never public. Ports 587 and 465 when the [SMTP relay](/transactional/smtp-relay/) is on; they are off by default. |
| Outbound  | HTTPS to your sending providers' APIs and to every other service you connect (payments, stores, AI models, HostRepute).                                                                                                                           |
| Outbound  | DNS lookups for authentication checks, blocklists and the MX records that tell which [mailbox provider](/reference/glossary/#mailbox-provider) hosts a contact's domain (Google Workspace counts as Gmail, Microsoft 365 as Outlook). Without DNS, company domains stay Other for routing, throttles and reports. Spamhaus refuses queries that arrive through public resolvers, so point `dns.servers` at a resolver of your own when you rely on blocklist checks (see [blocklists](/deliverability/blocklists/)). |
| Outbound  | `https://api.github.com` once a day for the release check. Turn it off with `updates.check: false` or in <UiPath path="shell.userMenuInstanceAdmin > admin.instance" />.                                                                         |

## Storage

| What                                          | Where                                                                                                                                                                                                                                                         |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PostgreSQL data                               | Contacts, campaigns, events, the job queue and the audit log. Size it for your contact count and event volume; [limits and defaults](/reference/limits-and-defaults/) lists how long each kind of data is kept.                                           |
| Secret key (`secrets.key_file`)               | `/var/lib/reputecast/secret.key` in the image, `data/secret.key` under the working directory for the binary. Created on first start unless you set `secrets.key`. Without it, stored provider credentials can't be decrypted: [back it up](/self-hosting/backups/). |
| Uploaded files (`files.dir`)                  | A `files` folder next to the secret key (`/var/lib/reputecast/files` in the image): digital products and lead magnets. Every web and worker process needs the same folder.                                                                                   |

## Notes

- PostgreSQL 18 images keep their data in `/var/lib/postgresql`, not `/var/lib/postgresql/data`; mount the volume there.
- The image has no shell; its health check runs the ReputeCast binary. Load balancers probe `/healthz` and `/readyz` over HTTP ([health checks, metrics and logs](/self-hosting/monitoring/)).
- One process runs every role by default. [Scale with web, ingest and worker roles](/self-hosting/scaling/) when you need more throughput.
- [PostgreSQL](/self-hosting/postgres/) covers managed databases, connection pools and the role SQL segments need.
