To scale ReputeCast, you run the same binary as several processes, each with some of its three roles, all sharing one
PostgreSQL database. One process with every role is the default and is enough for most instances; split the roles
when sending, webhook traffic or the web app need more capacity than one machine gives.

<ArchitectureDiagram />

One binary serves the browser, the API, MCP agents and providers' webhooks, and runs the background jobs; PostgreSQL
holds the data and the job queue, and the sending providers deliver the mail.

## The roles

| Role     | What it runs                                                                                                                                                                                   |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `web`    | The web app, the API under `/api/`, public pages (`/p/…`, `/t/…`, `/r/…`), `/mcp`, sign-in callbacks, Let's Encrypt challenges and the [SMTP relay](/transactional/smtp-relay/).                |
| `ingest` | Webhooks from sending providers and connected services under `/hooks/…`: it checks each one, stores it and answers `200` at once.                                                              |
| `worker` | The job queue in PostgreSQL: sends, event processing, syncs, health checks, warm-up, automations, imports, reports and retention. Scheduled jobs run only in worker processes.                  |

- `reputecast serve` runs all three; `serve --role=web,ingest` (or `REPUTECAST_ROLES=web,ingest`) runs some;
  `reputecast worker` is the same as `serve --role=worker`.
- Only a process that runs `web` or `ingest` has the HTTP listener. Every process opens the metrics listener (`:9464`),
  where a worker-only process also answers `/healthz` and `/readyz`, so the image's health check works for it too.

## Before you begin

- ReputeCast runs as one process, installed with [Docker Compose](/self-hosting/docker/) or
  [the binary](/self-hosting/binary/), and you have a [backup](/self-hosting/backups/).
- Your PostgreSQL accepts the extra connections ([size the pool](/self-hosting/postgres/#size-the-connection-pool)).

## Split the roles

<Steps>

1. Give every process the same configuration: `database.url`, `http.public_url`, `http.trusted_proxies` and the same
   secret key. On several machines, set `secrets.key` (`REPUTECAST_SECRETS__KEY`) on all of them instead of a key
   file; with Docker, copy the existing key out with `docker compose cp app:/var/lib/reputecast/secret.key .` and use
   its contents.

2. Give web and worker processes the same `files.dir` (product files, lead magnets, uploads in progress and
   exports), on a shared volume or network file system. Without one, keep the files in an
   [S3-compatible bucket](/self-hosting/object-storage/) with `storage.backend: s3` on every process. Available from
   the next release after 1.6.0.

3. Run one or more `serve --role=web,ingest` processes behind your [reverse proxy](/self-hosting/reverse-proxy/), and
   at least one `worker`. Several workers share the queue through PostgreSQL. To grow webhook capacity separately, run
   `--role=ingest` processes and route `/hooks/` to them in the proxy.

4. Apply migrations from one place: one process with `--auto-migrate`, or `reputecast migrate up` before you start the
   new version everywhere. Several processes started with `--auto-migrate` take turns, so each migration runs once. A
   `worker` never migrates; started on an older schema, it waits until the migrations land.

5. Run the same ReputeCast version in every process.

</Steps>

The shipped `docker-compose.yml` carries this split, commented out. As an override file, it runs the web and ingest
roles in `app` and the jobs in a separate `worker` container, on one server, sharing the `appdata` volume (secret key
and files):

```yaml title="docker-compose.override.yml"
services:
  app:
    command: ["serve", "--role=web,ingest", "--auto-migrate", "--auto-install"]

  worker:
    image: ${REPUTECAST_IMAGE:-ghcr.io/hostrepute/reputecast}:${REPUTECAST_VERSION:-latest}
    restart: unless-stopped
    command: ["worker"]
    depends_on:
      app:
        condition: service_healthy
    environment:
      REPUTECAST_DATABASE__URL: postgres://reputecast:${POSTGRES_PASSWORD:-reputecast}@postgres:5432/reputecast?sslmode=disable
      REPUTECAST_PUBLIC_URL: ${REPUTECAST_PUBLIC_URL:-http://localhost:8080}
    volumes:
      - appdata:/var/lib/reputecast
    healthcheck:
      test: ["CMD", "/usr/local/bin/reputecast", "healthcheck"]
      interval: 15s
      timeout: 5s
      retries: 4
```

The worker starts once `app` is healthy, so the secret key and the migrations are in place.

## Split the roles on Kubernetes

On Kubernetes, the chart you install with Helm ([Kubernetes](/deploy/kubernetes/)) runs the same split as Deployments
with `mode: split`: web pods (2 by default,
with an optional autoscaler), worker pods (1) and, with `ingest.separate`, webhook ingest pods that the Ingress routes
`/hooks/` to. Pods don't share a folder, so split mode needs `storage.backend: s3` and stops the install without it;
migrations run in a Job before every install and upgrade. Available from the next release after 1.6.0.

<Aside type="caution">
  Split an instance after its first start, when the secret key file exists. A worker that starts on an empty volume
  before the app could create a different key.
</Aside>

## What the processes share

- **PostgreSQL**: data, the job queue and job scheduling. Each process opens up to `database.max_conns` connections
  (default 20) and `worker.concurrency` (default 50) sets how many jobs a worker runs at once.
- **Settings saved in the app**: every process reads the public URL saved in Instance admin again every 30 seconds,
  and installed community adapters every 15 seconds.
- **Files**: `files.dir`, or the bucket, as above. Every process must use the same backend.
- **Not the rate limits**: each web process counts requests on its own, so behind a load balancer with three web
  processes a caller can reach three times the [limits](/self-hosting/security/#defaults-and-limits).

## Measured performance

On the load test data (a million contacts, 3.2 million delivery events), ReputeCast and PostgreSQL 16 on one host with
4 vCPUs answered a contacts page in 6–7 ms, a search in 23 ms, the report of a campaign to 975,000 recipients in 272 ms
and a two-condition segment count in 927 ms. Under load, on a 4-vCPU GitHub runner with PostgreSQL 18 and k6 on the
same host, every target was met (1 November 2026):

| Load test                                  | p95    | Target       |
| ------------------------------------------ | ------ | ------------ |
| Contacts pages, 10 people, 278 requests/s  | 35 ms  | under 200 ms |
| Contacts search, the same                  | 140 ms | under 150 ms |
| Ten people browsing                        | 140 ms | under 200 ms |
| Segment counts                             | 5 ms   | under 2 s    |
| Send API, 135 messages/s                   | 247 ms | under 300 ms |

To measure your own hardware, use a development instance (`REPUTECAST_ENV=development`): after `reputecast seed`,
`reputecast seed --sample load --contacts 1000000` adds a "Load test" workspace of that size, in about 8 minutes and
3 GB. The k6 scripts in the repository's `loadtest/k6` folder drive the contacts list, segment counts, the send API and
webhook ingest against it.

## Check that it worked

- `curl http://<web process>:8080/readyz` answers `ready` on every web and ingest process.
- `docker compose ps` shows `worker` as `healthy`: its `/readyz` on port 9464 answers once its workers run.
- The `http listening` log line of each web process shows its roles, and each worker logs `workers started` with its
  concurrency.
- Scheduled sends start and the live monitor moves: workers are processing the queue.

## Troubleshooting

- **Nothing is sent and imports never finish**: no process runs the `worker` role.
- **Stored provider credentials can't be decrypted in one process**: its secret key differs; give every process the
  same `secrets.key` or key file.
- **Product downloads fail from some processes**: `files.dir` is not shared, or the processes don't all use the same
  `storage.backend`.
- **`FATAL: sorry, too many clients already`**: lower `database.max_conns` per process.
- **A process logs `metrics listener not started`**: another process on the host already holds port 9464. Give each
  process on a host its own `metrics.addr`.
- **A worker stays unhealthy with `workers not started`, or `database schema behind this release`**: the migrations
  haven't run yet; start `app` with `--auto-migrate` or run `reputecast migrate up`.
