This page covers the PostgreSQL setup for ReputeCast: the database, its users, the connection and the schema
migrations. ReputeCast keeps everything in PostgreSQL, including its job queue, and needs one extension, `pg_trgm`, for
contact search.

## Before you begin

- PostgreSQL 16, 17 or 18, self-managed or from a cloud provider.
- An administrator account on it (for example `postgres`) to create the database and roles.
- The [Docker Compose stack](/self-hosting/docker/) already runs PostgreSQL 18 as a superuser `reputecast`, which
  creates everything below by itself; this page is for any other database.

## Create the database

<Steps>

1. As an administrator, create the app user, its database and the role SQL segments run as:

   ```sql title="setup.sql"
   CREATE ROLE reputecast LOGIN PASSWORD 'change-me';
   CREATE DATABASE reputecast OWNER reputecast;
   CREATE ROLE reputecast_segments NOLOGIN;
   GRANT reputecast_segments TO reputecast;
   ```

   Create `reputecast_segments` now, before the first migration: see [SQL segments](#sql-segments).

2. Point ReputeCast at the database with `database.url` (`REPUTECAST_DATABASE__URL`, or `DATABASE_URL`):

   ```txt
   postgres://reputecast:change-me@db.internal:5432/reputecast?sslmode=require
   ```

   - Use `sslmode=require` (or `verify-full` with the provider's CA) when the database is on another machine;
     `sslmode=disable` only on the same host or a private Docker network.
   - Percent-encode characters such as `@`, `:` and `/` in the password, or pick a password without them.

3. Run the migrations and create the first Owner with `reputecast install` (the Docker image does both at start).

</Steps>

## Managed PostgreSQL

Cloud databases usually give you an administrator that is not a superuser. ReputeCast works with that:

- The migrations need only ownership of the database. The one extension they create, `pg_trgm`, comes with PostgreSQL
  and is trusted, so the database's owner can create it
  ([pg_trgm documentation](https://www.postgresql.org/docs/current/pgtrgm.html), checked November 2026).
- Creating `reputecast_segments` needs the `CREATEROLE` privilege. If the app's user doesn't have it, create the
  role with the administrator before the first start (step 1 above); otherwise ReputeCast installs fine, but SQL
  segments stay off.

## Size the connection pool

Each ReputeCast process opens its own pool of up to `database.max_conns` connections (default 20). Command-line
commands open a few more while they run (`migrate` and `install` 4, `user` 2). Keep the total below PostgreSQL's
`max_connections` (100 by default), with room for your own tools:

| Processes                                      | Connections at most |
| ---------------------------------------------- | ------------------- |
| One `serve` (all roles), default pool          | 20                  |
| Three `serve --role=web,ingest` and one worker | 4 × 20 = 80         |

Lower `database.max_conns` per process, or raise `max_connections`, when you [add processes](/self-hosting/scaling/).

Each connection runs `SET jit = off` once it connects: ReputeCast's queries are short, and compiling them with JIT
took longer than running them. It is set after connecting, not in the startup packet, so poolers such as PgBouncer
accept the connection.

## SQL segments

[SQL segments](/audience/segments/) run a member's `SELECT` as `reputecast_segments`, a role that can read nothing on
its own, inside a read-only transaction with a statement timeout. When the role is missing, the segment builder says
SQL segments are turned off on this database.

The migrations set SQL segments up when the role exists and the app's user is a member of it. Create it with the
commands ReputeCast prints, replacing `<app user>` with the user in `database.url`:

```sql title="As an administrator"
CREATE ROLE reputecast_segments NOLOGIN;
GRANT reputecast_segments TO <app user>;
```

- **Before the first start** (recommended): run them, then install ReputeCast. Nothing else is needed.
- **On a database that is already migrated**, or after restoring a backup on a new server, `reputecast migrate up`
  alone doesn't finish the job: the migration that creates the segment runner has already been recorded. After the two
  commands, hand the runner to the role with the server's environment, then restart every ReputeCast process (each
  checks for the runner once, when it first needs it):

  ```sh
  reputecast migrate segments-role
  ```

  It is safe to run again, and prints the state of the role, as `reputecast doctor` does on its
  `SQL segments role` line.

The role is shared by every database on the server, and `pg_dump` doesn't include roles: create it on a new server
before you [restore a backup](/self-hosting/backups/#restore).

## Monthly partitions of delivery_events

`delivery_events` holds every send, delivery, bounce, open and click, and is the largest table on most instances.
Since 1.3.0 it is split by month on `received_at`, when ReputeCast stored the event, so each month's indexes stay small
and [data retention](/team/workspaces/#set-data-retention) clears a month's open and click details in one pass.

- The upgrade to 1.3.0 converts the table (`migrate up` and `serve --auto-migrate`), unless
  `reputecast migrate partition-events` already did. Nothing is copied: the existing table becomes
  `delivery_events_legacy`, the partition of everything before the first month, and later months get partitions of
  their own.
- An hourly maintenance job keeps the current month and the next two ready; `delivery_events_default` catches anything
  outside them, so an insert never fails.
- Dedupe keys move to `delivery_event_keys` and are kept 180 days. The upgrade then drops the old unique index,
  `delivery_events_dedupe_key`, concurrently.
- The conversion holds the migration lock, runs while ReputeCast runs and can run again after an interruption. Two
  steps read the whole table without blocking writes; the swap waits at most 10 seconds for the table's lock, tried 5
  times. On a million contacts with 3.2 million events (1.4 GB) it took 5 seconds.

To choose the moment on a very large table, [back up](/self-hosting/backups/), then convert it before you upgrade, at a
quiet hour:

```sh
reputecast migrate partition-events
```

### Undo the conversion

Version 1.2 works on the partitioned table too, so a rollback doesn't need this. To undo the conversion, restore the
backup taken before it, or run this as the app user in one transaction:

```sql title="Undo the partitioning"
BEGIN;
LOCK TABLE delivery_events IN ACCESS EXCLUSIVE MODE;
ALTER TABLE delivery_events DETACH PARTITION delivery_events_legacy;
ALTER TABLE delivery_events_legacy DROP CONSTRAINT delivery_events_before_partitions;
INSERT INTO delivery_events_legacy SELECT * FROM delivery_events;  -- the newer months' rows
DROP TABLE delivery_events;                                         -- and its monthly partitions
ALTER TABLE delivery_events_legacy RENAME TO delivery_events;
ALTER TABLE delivery_events DROP CONSTRAINT delivery_events_legacy_pkey;
ALTER TABLE delivery_events ADD CONSTRAINT delivery_events_pkey PRIMARY KEY (id);
COMMIT;
```

Then rename each index whose name ends in `_legacy` back without the suffix.

<Aside type="caution">
  `DROP TABLE delivery_events` drops the monthly partitions: take a backup first. A 1.3 release converts the table again
  at its next `migrate up` or `--auto-migrate` start.
</Aside>

## Migrations

The binary carries every schema migration: ReputeCast's own, then those of its job queue.

- `reputecast migrate up` applies what is pending and prints `Database is up to date.`; `reputecast install` and
  `serve --auto-migrate` (the Docker image's default) do the same at start.
- `reputecast migrate status` lists each migration with its applied date or `pending`.
- `reputecast migrate down` rolls back only the latest ReputeCast migration. It is meant for development: down
  migrations drop data. Restore a backup to go back.
- A few migrations build an index concurrently, outside a transaction, so imports, sign-ups and sends keep going while
  the index builds on a large table.
- Migrations hold a lock, so processes started together migrate once. A process whose database still misses migrations
  serves read-only until they're applied ([while migrations are pending](/self-hosting/upgrades/#while-migrations-are-pending)).

## Check that it worked

- `/readyz` answers `ready`; it answers `503 database unavailable` when a database ping takes longer than 2 seconds.
- `reputecast migrate status` shows no `pending` line, and `reputecast doctor` shows `ok` for the database, the schema
  and the SQL segments role.
- In <UiPath path="nav.audience > audience.tabSegments" />, a segment in SQL mode counts contacts.

## Troubleshooting

- **`connect to postgres: …` at start**: wrong host, password or `sslmode`; test the same URL with `psql`.
- **`FATAL: sorry, too many clients already`**: the pools exceed `max_connections`; lower `database.max_conns`.
- **SQL segments stay off after you created the role**: the database was migrated before; run
  `reputecast migrate segments-role` and restart ReputeCast.
