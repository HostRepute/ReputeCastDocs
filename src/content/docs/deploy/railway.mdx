This guide runs ReputeCast on Railway as two services in one project, Railway's PostgreSQL database and the ReputeCast
Docker image, with a volume for uploaded files and HTTPS on a Railway domain or your own. Create the project with the
Railway CLI from the repository's configuration, or by hand in the dashboard.

## Before you begin

- A Railway account on a paid plan (Hobby or Pro). The Free plan allows one volume per project, which the PostgreSQL
  template uses. A Trial works for a test, but a Limited Trial (unverified account) restricts the outbound network
  access ReputeCast needs to reach sending providers.
- Docker or OpenSSL on your computer, to generate the secret key. See also the
  [system requirements](/self-hosting/requirements/).

## Deploy with the Railway CLI

The repository's `deploy/railway/railway.ts` describes the project as Railway
[Infrastructure as Code](https://docs.railway.com/infrastructure-as-code) (checked November 2026). Available from the
next release after 1.6.0.

<Steps>

1. Install the Railway CLI, version 5.42.1 or later, and sign in with `railway login`.

2. In a checkout of the repository, install the configuration's library and link a new, empty project:

   ```sh
   git clone --depth 1 https://github.com/hostrepute/reputecast.git && cd reputecast
   npm install --prefix deploy/railway --no-save railway@3
   railway link
   ```

3. Apply the configuration with the first Owner's email:

   ```sh
   REPUTECAST_ADMIN_EMAIL=you@company.com railway config apply --file deploy/railway/railway.ts
   ```

   It creates the `Postgres` database and the `ReputeCast` service from `ghcr.io/hostrepute/reputecast:latest`, with
   the volume `reputecast-data` at `/var/lib/reputecast`, the health check `/readyz` with a 300-second timeout, and
   these variables: `DATABASE_URL=${{Postgres.DATABASE_URL}}`, `REPUTECAST_PUBLIC_URL=https://${{RAILWAY_PUBLIC_DOMAIN}}`,
   `REPUTECAST_ADMIN_EMAIL`, `REPUTECAST_HTTP__TRUSTED_PROXIES=private`
   ([trusted proxies](/deploy/overview/#trusted-proxies)), `PORT=8080` and `RAILWAY_RUN_UID=0`.

4. In the ReputeCast service's **Settings** → **Networking** → **Public Networking**, click **Generate Domain** with
   port `8080`. The public URL follows that domain.

5. Read the first Owner's temporary password in the deployment's logs and sign in, as steps 10 and 11 of
   [deploy by hand](#deploy-reputecast-by-hand) describe.

</Steps>

ReputeCast creates its secret key on the volume at the first start, as `/var/lib/reputecast/secret.key`: back the
volume up with the database in the service's **Backups**. To keep the key outside Railway too, deploy by hand with
`REPUTECAST_SECRETS__KEY`.

## Deploy ReputeCast by hand

<Steps>

1. On the Railway dashboard, click **New Project** and choose **Empty Project**.

2. Click **+ New**, then **Database**, then **PostgreSQL**. Railway deploys PostgreSQL 18 as a service named `Postgres`,
   with its own volume and a `DATABASE_URL` variable that uses the private network.

3. Click **+ New**, then **Docker Image**, enter `ghcr.io/hostrepute/reputecast:v1.6.0`, press Enter and click
   **Deploy**. This first deployment fails because the service has no settings yet.

4. Generate the secret key on your computer and save it in your password manager. Both commands print a key in the
   same format (44 characters ending in `=`): `docker run --rm ghcr.io/hostrepute/reputecast:v1.6.0 secrets generate-key`
   or `openssl rand -base64 32`.

5. Open the ReputeCast service. In **Settings** → **Networking** → **Public Networking**, click **Generate Domain**
   (if Railway asks for a port, enter `8080`, not 9464: that is the metrics port, which stays private). Railway serves
   the `*.up.railway.app` domain over HTTPS.

6. On the **Variables** tab, click **Raw Editor**, paste these lines with your email and key, and save:

   ```sh title="Raw Editor"
   REPUTECAST_DATABASE__URL=${{Postgres.DATABASE_URL}}
   REPUTECAST_PUBLIC_URL=https://${{RAILWAY_PUBLIC_DOMAIN}}
   REPUTECAST_ADMIN_EMAIL=you@company.com
   REPUTECAST_SECRETS__KEY=paste-the-key-from-step-4
   PORT=8080
   RAILWAY_RUN_UID=0
   ```

   - `${{Postgres.DATABASE_URL}}` references the database's connection string (`Postgres` is the service's name).
     Keep it as it is: without an `sslmode` parameter, ReputeCast uses the TLS that Railway's PostgreSQL image turns on.
   - `${{RAILWAY_PUBLIC_DOMAIN}}` is the domain from step 5. With [your own domain](#use-your-own-domain), write the
     URL instead.
   - `REPUTECAST_ADMIN_EMAIL` is the first Owner's email, used only while the database has no users.
   - `PORT=8080` tells Railway's health check which port to call. The image listens on 8080 whatever `PORT` says,
     because it sets `REPUTECAST_HTTP__ADDR=:8080`, which wins over `PORT`.
   - `RAILWAY_RUN_UID=0` runs the app as root: Railway mounts volumes owned by root, which the image's user
     (uid 65532) can't write to.
   - Railway doesn't document the address range of its edge proxy, so leave `REPUTECAST_HTTP__TRUSTED_PROXIES` unset
     with 1.6.0 ([trusted proxies](/deploy/overview/#trusted-proxies)). The CLI configuration sets the `private`
     keyword instead, which trusts Railway's private network. Available from the next release after 1.6.0. Other
     settings: [configuration](/self-hosting/configuration/).

7. Right-click the project canvas (or press <kbd>⌘</kbd> <kbd>K</kbd> or <kbd>Ctrl</kbd> <kbd>K</kbd>), create a
   volume, connect it to the ReputeCast service and set its mount path to `/var/lib/reputecast`.

8. In **Settings** → **Deploy**, set **Healthcheck Path** to `/readyz`. Railway then waits up to 300 seconds for a
   `2xx` answer before it sends traffic to a new deployment; ReputeCast gives one once it reaches the database, its
   schema has every migration and its workers run.

9. Click **Deploy** in the canvas banner that lists the staged changes. On its first start, ReputeCast applies the
   database migrations and creates the first Owner.

10. On the **Deployments** tab, click the deployment to open its logs and filter them for `Password`. With the Railway
    CLI, in a folder linked to the project: `railway logs --lines 500 --filter "Password"`.

    ```txt title="Deploy logs"
      ReputeCast is installed.

      Sign in at  https://reputecast-production-1a2b.up.railway.app
      Email       you@company.com
      Password    SHLn-zHfR-cf6j-NEm5   (temporary: you'll replace it at first sign-in)
    ```

11. Open the public URL and sign in. The [first sign-in](/self-hosting/first-run/) asks you to replace the password,
    add a passkey or an authenticator app, save recovery codes, confirm the instance basics and create a workspace.

</Steps>

<Aside type="caution">
  Keep a copy of `REPUTECAST_SECRETS__KEY` outside Railway: without it, the provider credentials stored in the database
  can't be decrypted. To hide it in the dashboard, choose **Seal** in the variable's three-dot menu (a sealed variable
  can't be read back or unsealed).
</Aside>

### Use your own domain

1. In **Settings** → **Networking** → **Public Networking**, click **+ Custom Domain**, enter the domain (such as
   `news.example.com`) and choose port `8080`.
2. Create both records Railway shows, a `CNAME` and a `TXT`, at your DNS host. Railway verifies the domain (green check
   mark) and issues a Let's Encrypt certificate, usually within an hour.
3. On the **Variables** tab, set `REPUTECAST_PUBLIC_URL=https://news.example.com` and deploy the change. Do this
   before the first sign-in: ReputeCast ties passkeys to the public URL's domain and puts it in every link it sends.
   After it, also change the address in <UiPath path="shell.userMenuInstanceAdmin > admin.instance" />: the one saved
   there wins over the variable, and saving it moves the provider webhooks.

Behind Cloudflare's proxy, set Cloudflare's SSL/TLS mode to **Full**; Railway says **Full (Strict)** doesn't work as
intended. The Trial plan allows 1 custom domain, the Hobby plan 2 per service.

## Check that it works

- The **Deployments** tab shows the deployment as `Active`: the `/readyz` health check passed.
- `curl https://news.example.com/readyz` answers `ready`, or `database unavailable` (status 503) when ReputeCast can't
  reach PostgreSQL. Railway calls `/readyz` only while a deployment starts, so point an uptime monitor at it for ongoing
  checks ([monitoring](/self-hosting/monitoring/)).

## Upgrade

1. Read the release notes and [back up](/self-hosting/backups/). The PostgreSQL service's **Backups** tab backs up its
   volume by hand or on a daily, weekly or monthly schedule.
2. In the ReputeCast service's **Settings** → **Source** → **Source Image**, click the edit icon and change the tag, for
   example to `ghcr.io/hostrepute/reputecast:v1.6.0`. A service created with the CLI runs `latest`: redeploy it to
   pull the image again. When Railway shows an update for the image, its upgrade button
   stages the new tag for you.
3. Click **Deploy**. ReputeCast applies new migrations when it starts. A service with a volume never runs two
   deployments at once, so expect a short downtime. Upgrading to 1.3.0 converts `delivery_events` to monthly partitions
   and holds the migration lock while it runs ([upgrade to 1.3.0](/self-hosting/upgrades/#upgrade-to-130)); on a very
   large table, give the health check more than 300 seconds with a `RAILWAY_HEALTHCHECK_TIMEOUT_SEC` variable
   ([healthchecks](https://docs.railway.com/deployments/healthchecks), checked November 2026).

To let Railway apply new releases in a maintenance window, use **Configure Auto Updates** in the same section
([upgrade ReputeCast](/self-hosting/upgrades/)).

## Troubleshooting

- **`Error: secret key file /var/lib/reputecast/secret.key: open /var/lib/reputecast/secret.key: permission denied`**:
  the volume is owned by root and `REPUTECAST_SECRETS__KEY` isn't set. Set the key and `RAILWAY_RUN_UID=0`, then deploy.
- **The domain shows "Application failed to respond" or `404 page not found`**: the domain's target port isn't 8080
  (9464 is the metrics port). In **Settings** → **Networking**, click the edit icon next to the domain and set `8080`.
- **The deployment fails its health check**: `/readyz` didn't answer `ready` in time. It answers `database unavailable`
  while ReputeCast can't reach PostgreSQL: check that `REPUTECAST_DATABASE__URL` names the database service as the
  canvas shows it, in the same environment. If the deploy logs show migrations still running, raise
  `RAILWAY_HEALTHCHECK_TIMEOUT_SEC` and deploy again.
- **An SMTP sending provider can't connect**: Railway turns off outbound SMTP on the Free, Trial and Hobby plans. Use a
  provider with an HTTPS API, such as Amazon SES, Postmark or Resend, or move to Pro and redeploy.
