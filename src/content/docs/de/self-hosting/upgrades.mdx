Um ReputeCast zu aktualisieren, ersetzen Sie das Image oder die Binärdatei durch ein neueres Release und lassen es seine
Datenbankmigrationen anwenden; alles andere (Konfiguration, geheimer Schlüssel, Daten) bleibt, wie es ist.

## Installierte Version ansehen

Ein [Instanz-Admin](/de/reference/glossary/#instance-admin) sieht die installierte Version, das neueste Release und
dessen Changelog unter <UiPath path="shell.userMenuInstanceAdmin > admin.instance" /> in der Karte
<UiPath path="admin.versionCard" />. Auf der Kommandozeile gibt `reputecast version` dasselbe aus:
`reputecast <version> (<commit>) <Go version>`.

<Screenshot

/>

- Das Badge <UiPath path="admin.updateAvailable" /> erscheint, wenn das neueste Release neuer ist als die installierte
  Version. Builds ohne Release-Versionsnummer (etwa `dev`) zeigen es nie.
- Unter <UiPath path="admin.upgradeOnServer" /> zeigt die Karte den Befehl für Docker Compose
  `cd /opt/reputecast && docker compose pull && docker compose up -d`. Ersetzen Sie `/opt/reputecast` durch den Ordner,
  der Ihre `docker-compose.yml` enthält. Betreibt jemand anderes den Server und setzt `updates.managed_by`, nennt die
  Karte statt des Befehls, wer die Upgrades verwaltet
  ([Einstellungen, die der Serverbetreiber verwaltet](/de/self-hosting/instance-admin/#einstellungen-die-der-serverbetreiber-verwaltet)).
- Der Schalter <UiPath path="admin.updateCheck" /> ruft einmal täglich das neueste Release von `api.github.com` ab. Die
  Anfrage enthält keine Versionsnummer und keine Instanz-ID; es ist der einzige ausgehende Aufruf, den ReputeCast von
  sich aus macht. Schalten Sie ihn hier ab, oder setzen Sie `updates.check: false` in der
  [Konfiguration](/de/reference/configuration/), um ihn für die ganze Instanz abzuschalten (der Schalter ist dann aus
  und gesperrt, ebenso das Kontrollkästchen bei der ersten Anmeldung).

## Bevor Sie beginnen

- Lesen Sie die [Versionshinweise](/de/reference/release-notes/) jeder Version zwischen Ihrer und der neuen, auch auf
  der [Release-Seite von GitHub](https://github.com/hostrepute/reputecast/releases).
- [Sichern Sie die Datenbank und den geheimen Schlüssel](/de/self-hosting/backups/). Migrationen ändern das Schema, und
  eine Sicherung ist der verlässliche Weg zurück.
- Planen Sie eine kurze Unterbrechung ein, während die App neu startet. Beim Stoppen (`SIGTERM`, ein erneutes
  Deployment) holt ein Worker keinen neuen Job mehr und gibt laufenden Jobs 10 Sekunden zum Abschließen; ein Versand
  stoppt zwischen zwei Batches, wobei der gerade laufende Batch gesendet und erfasst wird.

## Upgrade durchführen

<Tabs syncKey="install">
<TabItem label="Docker Compose">

<Steps>

1. Wechseln Sie in den Ordner mit Ihrer `docker-compose.yml` und erstellen Sie eine Sicherung:

   ```sh
   docker compose exec -T postgres pg_dump -U reputecast -d reputecast -Fc > reputecast-before-upgrade.dump
   ```

2. Wenn Sie in `.env` eine Version festlegen (`REPUTECAST_VERSION=v1.5.0`), ändern Sie sie auf das Tag des neuen
   Releases. Die Image-Tags sind die Release-Tags mit ihrem führenden `v`, dazu `latest`. Ohne `REPUTECAST_VERSION`
   verwendet die Compose-Datei `latest`.

3. Laden Sie das neue Image und erstellen Sie den App-Container neu:

   ```sh
   docker compose pull && docker compose up -d
   ```

   Das Image startet mit `serve --auto-migrate` und wendet daher ausstehende Migrationen an, bevor es Anfragen
   beantwortet. Die Protokolle zeigen eine Zeile `migration applied` pro Migration, und `docker compose ps` zeigt `app`
   als `healthy`, sobald die App bereit ist.

</Steps>

</TabItem>
<TabItem label="Binärdatei">

<Steps>

1. Erstellen Sie eine Sicherung (siehe [Sichern und wiederherstellen](/de/self-hosting/backups/)).

2. Laden Sie das Archiv für Ihre Plattform und `checksums.txt` von der
   [Release-Seite](https://github.com/hostrepute/reputecast/releases) herunter und prüfen Sie den Download:

   ```sh
   sha256sum --ignore-missing -c checksums.txt
   ```

3. Stoppen Sie jeden ReputeCast-Prozess, zum Beispiel mit `sudo systemctl stop reputecast`.

4. Ersetzen Sie die Binärdatei (zum Beispiel `/usr/local/bin/reputecast`) durch die neue.

5. Wenden Sie die Migrationen einmal an, mit derselben Umgebung, die der Dienst verwendet:

   ```sh
   reputecast migrate up
   ```

   Der Befehl wendet die Migrationen von ReputeCast an, danach die der Job-Warteschlange, und endet mit
   `Database is up to date.`

6. Starten Sie jeden Prozess wieder. Wenn Sie [mehrere Rollen](/de/self-hosting/scaling/) betreiben, aktualisieren Sie
   alle auf dieselbe Version.

</Steps>

</TabItem>
</Tabs>

## Solange Migrationen ausstehen

Ein Prozess, dessen Datenbank Migrationen fehlen, die er braucht, etwa eine Binärdatei, die ersetzt wurde, bevor
`reputecast migrate up` lief, schreibt nicht in sie:

- Seiten und die API lesen wie gewohnt. Die App zeigt vor jeder Bearbeitung das Banner
  <UiPath path="shell.bannerMaintenance" />.
- Schreibvorgänge antworten mit `503` und dem Code `maintenance`. An- und Abmelden funktioniert weiterhin, und die
  Webhooks der Versandanbieter werden weiterhin gespeichert.
- Die Worker warten, daher wird nichts gesendet.
- `/readyz` antwortet mit `503`, sodass ein Load Balancer oder Orchestrator den Datenverkehr weiter an das vorherige
  Release schickt.

Der Prozess prüft alle 5 Sekunden erneut und macht von selbst weiter, sobald `reputecast migrate up` oder das
`--auto-migrate` eines anderen Prozesses sie angewendet hat. Browser-Tabs, die über ein Upgrade hinweg offen bleiben,
bieten <UiPath path="shell.bannerReload" /> an, um die neue Version zu laden.

Migrationen halten eine Sperre in PostgreSQL: Starten mehrere Prozesse mit `--auto-migrate`, wendet einer sie an,
während die anderen auf ihn warten (bis zu 15 Minuten), sodass jede Migration einmal läuft. Führen Sie sie über eine
direkte Verbindung oder eine Verbindung im Session-Modus aus, nicht über PgBouncer im Transaktionsmodus.

## Upgrade auf 1.5.0

Version 1.5.0 ändert auf dem Server Folgendes; die [Versionshinweise](/de/reference/release-notes/#150) listen den
Rest auf.

- **10 neue Migrationen** (`03400` bis `03446`) laufen beim ersten Start oder mit `reputecast migrate up`.
- **Zwei optionale Einstellungen** für eine Instanz, die Sie für andere betreiben: `http.public_url_locked` legt die
  öffentliche URL fest, und `updates.managed_by` nennt, wer die Instanz aktualisiert
  ([ReputeCast konfigurieren](/de/self-hosting/configuration/)). Solange Sie sie nicht setzen, ändert sich nichts.
- **Die Callback-URL von WhatsApp endet mit einem Token**, `<public URL>/hooks/whatsapp/<workspace>/<token>`. Ein
  Konto, das vorher verbunden wurde, behält seine alte Adresse, `<public URL>/hooks/whatsapp/<workspace>`, bis Meta
  die neue aufruft, sodass beim Upgrade nichts stoppt. Um es umzustellen, öffnen Sie
  <UiPath path="nav.providers > channels.whatsapp" /> als Person, die Versandanbieter verwalten darf: Der Hinweis
  <UiPath path="whatsapp.oldAddressTitle" /> zeigt die neue Callback-URL zum Kopieren. Fügen Sie sie unter Meta for
  Developers › Ihre App › WhatsApp › Configuration als Callback-URL ein (das Verifizierungstoken bleibt gleich) und
  klicken Sie auf **Verify and save**. Ab dem ersten Aufruf von Meta an die neue URL lehnt die alte Adresse die
  Zustellungen des Kontos ab. Wer nach dem Umstellen auf ein früheres Release zurückrollt, muss die alte Adresse wieder
  in Meta einfügen: Frühere Releases kennen die neue nicht ([WhatsApp verbinden](/de/channels/whatsapp/)).
- **SNS-Nachrichten gelten nur noch aus dem eigenen Topic eines Anbieters als vertrauenswürdig.** Verbindungen zu
  Amazon SES haben ihr Topic seit dem Verbinden gespeichert. Ein Anbieter für AWS End User Messaging (SMS), dessen
  Webhook von Hand in AWS eingerichtet wurde, behält beim Upgrade das Topic, aus dem seine verifizierten Ereignisse
  kamen. Kamen sie aus mehreren Topics oder ist noch keines eingetroffen, werden seine Zustellbestätigungen und
  Antworten abgelehnt, bis SNS das Abonnement erneut bestätigt: Löschen Sie in der SNS-Konsole das HTTPS-Abonnement
  für die Adresse von ReputeCast und legen Sie es neu an, oder wählen Sie beim Anbieter
  <UiPath path="smsDialogs.registerAgain" />, wenn seine API Webhooks registrieren kann. Gespeichert wird das Topic der
  ersten Bestätigung.
- **Domains werden erneut geprüft.** Eine eigene Domain, eine Kurzlink-Domain für SMS oder eine Tracking-Domain für
  Links, die ein anderer Arbeitsbereich zuerst verifiziert hat, oder eine unter dem eigenen Host der öffentlichen URL
  wird nur mit dem TXT-Eintrag `_reputecast.<domain>` dieses Arbeitsbereichs verifiziert, zusätzlich zu ihrem `CNAME`.
  Eigene Domains und Kurzlink-Domains werden innerhalb von zehn Minuten nach dem Upgrade geprüft, Tracking-Domains
  innerhalb von 30. Solange eine solche Domain ihren TXT-Eintrag nicht hat, werden ihre Seiten nicht mehr
  ausgeliefert, SMS verwenden sie nicht für Links, und Links und das Öffnungspixel verwenden die öffentliche URL. Eine
  Tracking-Domain, die vor 1.5.0 von zwei Arbeitsbereichen verifiziert wurde, braucht den TXT-Eintrag des
  Arbeitsbereichs, der sie behält ([eigene Domains](/de/self-hosting/reverse-proxy/#eigene-domains)).

## Upgrade auf 1.3.0

Version 1.3.0 ändert auf dem Server Folgendes; die [Versionshinweise](/de/reference/release-notes/#130) listen den
Rest auf.

- **23 neue Migrationen** (`03360` bis `03388`); einige bauen Indizes nebenläufig (concurrently) auf. Eine legt die
  Extension `pg_trgm` für die Kontaktsuche an, die der Besitzer der Datenbank anlegen darf
  ([PostgreSQL](/de/self-hosting/postgres/#verwaltetes-postgresql)).
- **`delivery_events` wird in monatliche Partitionen aufgeteilt.** Nach den Migrationen wandeln `migrate up` und
  `serve --auto-migrate` die Tabelle mit jedem Versand, jeder Zustellung, jedem Bounce, jeder Öffnung und jedem Klick
  um, sofern `reputecast migrate partition-events` das nicht schon getan hat. Nichts wird kopiert, und
  Schreibvorgänge laufen weiter, aber zwei Schritte lesen die ganze Tabelle: Bei einer sehr großen Tabelle führen Sie
  `reputecast migrate partition-events` vorher selbst aus, zu einer ruhigen Stunde
  ([monatliche Partitionen](/de/self-hosting/postgres/#monatliche-partitionen-von-delivery_events)).
- **Schreibgeschützt bis zur Migration, und gesperrte Migrationen**, wie [oben](#solange-migrationen-ausstehen)
  beschrieben.
- **`/metrics` ist umgezogen** auf einen eigenen Listener, `:9464`. Hat Prometheus den Hauptport abgefragt, richten Sie
  es auf 9464 aus oder setzen Sie `metrics.token`
  ([Zustandsprüfungen, Metriken und Protokolle](/de/self-hosting/monitoring/)).
- **Eine Zustandsprüfung für den Container.** Das Image führt `reputecast healthcheck` aus, sodass Docker die App als
  `healthy` meldet, sobald `/readyz` antwortet.
- **Ratenlimits pro Browsersitzung.** Jeder angemeldete Browser hat eigene 600 Anfragen pro Minute; die Browser hinter
  einer Adresse teilen sich 6.000 ([Sicherheit und Härtung](/de/self-hosting/security/)).
- **nginx mit HTTP/2.** Das [Beispiel für nginx](/de/self-hosting/reverse-proxy/) schaltet jetzt HTTP/2 ein, wodurch
  die App auf Smartphones deutlich schneller lädt.

## Upgrade auf 1.2.0

Version 1.2.0 ändert auf dem Server Folgendes; die [Versionshinweise](/de/reference/release-notes/#120) listen den
Rest auf.

- **45 neue Migrationen** (`03000` bis `03350`) laufen beim ersten Start oder mit `reputecast migrate up`. Drei Indizes
  auf den Tabellen `contacts` und `messages` werden nebenläufig aufgebaut, sodass Importe, Anmeldungen und Versände
  weiterlaufen, während sie in einer großen Datenbank entstehen.
- **Ein Name für die öffentliche URL.** `REPUTECAST_PUBLIC_URL` setzt jetzt `http.public_url` für jede Art, ReputeCast
  zu betreiben, auch für die Binärdatei, und die mitgelieferte `docker-compose.yml` übergibt sie unverändert an die
  App. `REPUTECAST_HTTP__PUBLIC_URL`, ihr früherer Name, funktioniert weiterhin, wenn `REPUTECAST_PUBLIC_URL` nicht
  gesetzt ist.
- **DNS-Abfragen für Postfachanbieter.** ReputeCast ermittelt den Postfachanbieter eines Kontakts aus den MX-Einträgen
  seiner Domain, sodass Google Workspace als Gmail und Microsoft 365 als Outlook zählt. Nach dem Upgrade fragt ein
  Hintergrunddurchlauf alle 2 Minuten die Firmendomains bestehender Kontakte ab. Der Server braucht einen
  funktionierenden Resolver: den des Systems oder die Server in `dns.servers`
  ([Konfigurationsreferenz](/de/reference/configuration/)). Eine Domain, die noch nicht abgefragt wurde, zählt als
  Andere.
- **Geteilte Berichtslinks laufen ab.** Ansichtslinks für Berichte, die vor 1.2.0 erstellt wurden, liefen nie ab; jeder,
  der noch funktioniert, läuft jetzt 30 Tage nach dem Upgrade ab.
- **Standard-Antwortregeln.** Arbeitsbereiche ohne eigene Antwortregel erhalten unter
  <UiPath path="nav.providers > providers.tabTraffic" /> die Standard-Antwortregeln für Postfachanbieter (siehe
  [Traffic-Regeln](/de/providers/traffic-rules/)).

## Prüfen, ob es funktioniert hat

- <UiPath path="admin.versionCard" /> zeigt die neue Version als installiert.
- `reputecast migrate status` listet jede Migration mit einem Anwendungsdatum und keine als `pending`. In Docker:
  `docker compose exec app /usr/local/bin/reputecast migrate status`.
- `/readyz` antwortet `ready` ([Zustandsprüfungen, Metriken und Protokolle](/de/self-hosting/monitoring/)), und
  `reputecast doctor` meldet das Schema als `current`.

## Rollback durchführen

Die Rückkehr zum vorherigen Image oder zur vorherigen Binärdatei macht Migrationen nicht rückgängig: Die Datenbank
behält das neuere Schema. Innerhalb eines Minor-Releases (1.3.0 bis 1.3.2) fügen Migrationen nur hinzu, und über ein
Minor-Release hinweg (1.3 zu 1.2) läuft die ältere Binärdatei auf dem neueren Schema. Lesen Sie zuerst die
Versionshinweise: Ein Release, das etwas entfernt oder umbenennt, sagt das. Für weiter zurückliegende Versionen stellen
Sie die Sicherung wieder her.

- **Stellen Sie die Sicherung wieder her**, um exakt zum Zustand vor dem Upgrade zurückzukehren: Stoppen Sie
  ReputeCast, stellen Sie den erstellten Dump wieder her (siehe
  [Wiederherstellen](/de/self-hosting/backups/#wiederherstellen)) und starten Sie dann die Version, die Sie vorher
  betrieben haben. Nach dem Upgrade vorgenommene Änderungen gehen verloren.
- **Legen Sie die vorherige Version fest** (`REPUTECAST_VERSION` in `.env`, dann `docker compose up -d`), wie es die
  Karte <UiPath path="admin.versionCard" /> vorschlägt, wenn Sie die seit dem Upgrade geschriebenen Daten behalten
  wollen. 1.2 funktioniert auch mit dem partitionierten `delivery_events`.
- `reputecast migrate down` macht nur die neueste ReputeCast-Migration rückgängig, eine pro Aufruf, und lässt die
  Tabellen der Job-Warteschlange unberührt. Der Befehl ist für die Entwicklung gedacht: Down-Migrationen löschen Daten,
  führen Sie ihn daher nicht auf einer Produktionsdatenbank aus.

## Fehlerbehebung

- **Der neue Container beendet sich beim Start**: Lesen Sie `docker compose logs app`. Eine fehlgeschlagene Migration
  bricht den Start mit `migrate: …` ab; stellen Sie die Sicherung wieder her und melden Sie den Fehler mit der
  Release-Version.
- **Die App bleibt fehlerhaft, und `/readyz` antwortet `database schema behind this release`**: Kein Prozess hat die
  Migrationen angewendet. Führen Sie `reputecast migrate up` aus oder starten Sie einen Prozess mit `--auto-migrate`.
- **`migrate: another migrator held the lock for 15m0s`**: Ein anderer Prozess hat noch migriert, zum Beispiel ein
  großes `delivery_events` umgewandelt. Lassen Sie ihn fertig werden und starten Sie diesen dann erneut.
- **Die Versionskarte meldet, dass die Update-Prüfung fehlgeschlagen ist**: Der Server erreicht `api.github.com` nicht,
  oder GitHub hat mit einem Fehler geantwortet. Sonst ist nichts betroffen; die nächste Prüfung läuft am folgenden Tag.
- **Das neueste Release zeigt einen Strich**: Die Prüfung ist ausgeschaltet oder noch nicht gelaufen.
