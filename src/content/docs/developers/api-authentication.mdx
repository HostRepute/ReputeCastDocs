This page covers API key authentication for the ReputeCast REST API: the credentials it accepts, what a key may do,
where it may be called from, and how keys are created, rotated, revoked and refused. For a first call, follow [make
your first API call](/developers/api-quickstart/); the [client SDKs](/developers/sdks/) send the key for you.

## Send the key

Send the key in the `Authorization` header with the `Bearer` scheme on every request:

```http title="Request"
GET /api/v1/workspaces/acme-newsletter/campaigns HTTP/1.1
Host: reputecast.example.com
Authorization: Bearer rc_live_…
```

- When a request carries a bearer token, the key alone decides who is calling; session cookies are ignored.
- A key belongs to one [workspace](/reference/glossary/#workspace). Using it in another workspace's path answers
  `403` with the detail "This key belongs to another workspace."
- The only operation that needs no workspace in its path is [`GET /api/v1/integration`](/api/operations/get-integration/):
  it answers with the calling key's workspace slug, name and permissions.

## Credentials

Every secret is a prefix followed by 64 hexadecimal characters. ReputeCast shows it once, when it is created or
rotated, and stores only its SHA-256 hash.

The web app signs people in with the `rc_session` cookie. Scripts and services use keys.

## What a key may do

- **Permissions.** You pick 1 to 60 [permission](/reference/glossary/#permission) keys, the same keys roles use.
  You can grant only permissions you hold yourself; asking for more answers `403` with the code
  `escalation_denied`. Permissions that only people may hold never reach a key (see the holder rules in
  [permissions and roles](/reference/permissions/)).
- **Never more than the creator.** On every call, a key's permissions are cut down to what the member who created it
  holds at that moment. When the creator loses a permission, the key loses it too. When the creator leaves the
  workspace, the key keeps authenticating but every operation that needs a permission answers `403`; an integration
  key answers `owner_deactivated` instead, and someone with `integrations:manage` can take it over.
- **List scope.** A key can be limited to lists (up to 100; none means all lists). It can't reach lists outside its
  creator's own scope, at creation or later: on every call its lists and sender domains are cut down to what its
  creator reaches at that moment, so narrowing a member's scope narrows their keys at once (since 1.5.0).
- **Integration keys** work only for the operations of the triggers and actions turned on for their integration;
  any other call answers `403` with the code `integration_operation_denied`. Twelve operations accept only an
  integration's (or a WordPress site's) key.
- **People only.** Creating and rotating keys, approving sends, account security and Instance admin need a
  signed-in person, and so do the composer's comments and review links, dismissing a warning, continuing a send its
  canary phase held, asking to be emailed when a report's results are final, moving a scheduled campaign to another
  time, setting the workspace's marketing cap and sending a transactional template's test. A key calling them gets
  `403` with the code `humans_only`. These operations are not in the [API reference](/api/).
- **Acts as itself.** A key or MCP agent never stands in for the person who created it. The
  [audit log](/team/audit-log/) names the key or agent, and so does a [Send Readiness](/reference/glossary/#send-readiness)
  run it asks for: `ranBy` and `startedBy` hold its name, with `ranByType` or `startedByType` set to `api_key` or
  `mcp_agent`. The composer's list of people who have a campaign open shows only people; a key or agent is never in
  it and never counts as its creator being there.

The permission each operation needs is shown on its page in the API reference and in `x-permission` in the OpenAPI
document.

## Key lifecycle

Managing keys needs the `apikeys:manage` permission (MCP agents: `mcp:manage`). Creating and rotating happen in the
app, signed in.

<TableScroll label="Key lifecycle">

| Action                                | What happens                                                                                                                                                                                                                                                           |
| ------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Create                                | The secret is shown once. The audit log records `apikey.created` with the permissions and scope, never the secret.                                                                                                                                                    |
| <UiPath path="keys.rotate" />         | A new secret with the same name, permissions, scope and allowed IPs is shown once. **The old secret stops working at once.** A key with an expiry gets the same lifetime again, counted from today. Rotating an expired key replaces it.                                            |
| Rotate an integration key             | Use <UiPath path="nav.settings > settings.integrations" /> › <UiPath path="integrations.rotateKey" />: the old key keeps working for 24 hours. Rotating it in Keys & MCP answers `409` with the code `managed_by_integration`.                                       |
| <UiPath path="keys.revoke" />         | The key stops working at once; calls get `401`. You can create a replacement with the same permissions and scope in the same dialog.                                                                                                                                  |
| Expiry                                | After its expiry date the key answers `401`. Expired keys stay listed with the number of calls that still try to use them, so you can find what to update.                                                                                                             |
| Delete                                | Removes an expired or revoked key from the list. Active keys must be revoked first.                                                                                                                                                                                   |

</TableScroll>

The keys list shows when each key was last used and from which IP address. Actions a key takes appear in the
[audit log](/team/audit-log/) with the key as the actor.

## Limit a key to allowed IPs

A key can be limited to the addresses it is called from: up to 50 IPv4 or IPv6 addresses and networks, such as
`203.0.113.7`, `203.0.113.0/24` or `2001:db8::/48` (since 1.6.0). An empty list, the default, allows any address.
The same applies to send-only keys, SMTP credentials and [MCP agents](/developers/mcp/#limit-an-agent-to-allowed-ips).

<Steps>

1. In <UiPath path="nav.settings > settings.keys" />, select <UiPath path="keys.allowedIpsButton" /> on the key's
   row, or fill <UiPath path="keys.allowedIpsLabel" /> when you create the key.

2. Enter one address or network per line. The field shows where the key was last used and your own address as
   ReputeCast sees it, each with a link to add it.

3. Save. A list that leaves out the address the key was last used from asks first: calls from there stop at once.
   Choose <UiPath path="keys.saveAnyway" /> only if that caller should be refused.

</Steps>

How allowed IPs work:

- **The check comes after the token.** A known, valid key called from another address, or from an address ReputeCast
  can't tell, answers `403` with the code `ip_not_allowed`, and the detail names the address ReputeCast saw. An
  unknown key still answers `401`, so the check never tells anyone which keys exist. ReputeCast counts the refused
  calls with their address and client.
- **Behind a reverse proxy**, ReputeCast sees your callers' addresses only when the proxy is listed in
  `http.trusted_proxies` ([reverse proxy and TLS](/self-hosting/reverse-proxy/)); otherwise every call seems to come
  from the proxy. The dialog warns when requests arrive through a proxy that setting doesn't list.
- **Narrowing needs only `apikeys:manage`.** Letting the key be called from more places, by emptying the list or
  adding a network the old list doesn't cover, needs what rotating it needs: you hold every permission of the key,
  and its lists are within your own scope. Otherwise the answer is `403` with the code `escalation_denied`.
- **Integration keys never get a list**: Zapier, Make, n8n and WordPress call from their platforms' servers. Setting
  one answers `409` with the code `managed_by_integration`. A revoked key keeps its list.
- **Rotating keeps the list**, and every change is in the [audit log](/team/audit-log/) as `apikey.updated` with the
  list before and after.
- **SMTP credentials** outside their list are refused at login: the [SMTP relay](/transactional/smtp-relay/) answers
  `535 5.7.8` and names the address.

A signed-in person sets the list; the operation, `PUT /api/v1/workspaces/<workspace>/api-keys/<keyId>/allowed-ips`
with `{ "allowedIps": [ … ] }`, is not callable with an API key. The create call takes the same field as
`allowedIps`.

## Refused keys

A refused key answers `401` with the code `unauthenticated` and the header `WWW-Authenticate: Bearer realm="reputecast"`.
The `detail` says why:

| Situation                                        | `detail`                                                                 |
| ------------------------------------------------ | ------------------------------------------------------------------------ |
| No `Authorization` header and no session         | `Sign in to continue.`                                                   |
| A token without a ReputeCast key prefix          | `Unknown API key.`                                                       |
| An unknown or revoked key                        | `This API key is revoked or unknown.`                                    |
| An expired key                                   | `This API key expired on <date>. Rotate it in Settings › Keys & MCP.`    |

Integration keys answer `401` with the codes `key_revoked` and `key_expired` instead, and their detail names the
integration to reconnect. A valid key called from outside its [allowed IPs](#limit-a-key-to-allowed-ips) answers
`403` with the code `ip_not_allowed`. When the database can't confirm who is calling, the answer is `503` with the code
`unavailable`: retry, the key stays valid. Every code is listed in [errors](/developers/api-errors/).
