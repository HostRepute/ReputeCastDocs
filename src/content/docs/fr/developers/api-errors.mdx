Chaque appel en échec à l’API REST de ReputeCast répond avec un document de problème RFC 9457 : les
erreurs d’API RFC 9457 ci-dessous partagent une même forme JSON, servie en `application/problem+json`, avec un `code`
stable sur lequel votre programme peut s’appuyer. Le format est défini dans la
[RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) (vérifié en octobre 2026).

## Champs du problème

| Champ        | Type     | Signification                                                                                                                                                                                   |
| ------------ | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `status`     | integer  | Le code d’état HTTP, le même que celui de la réponse.                                                                                                                                           |
| `title`      | string   | Le texte de l’état HTTP, comme `Forbidden`.                                                                                                                                                     |
| `detail`     | string   | Une phrase sur laquelle une personne peut agir. Elle peut changer d’une version à l’autre et être dans la langue du lecteur : affichez-la, ne l’analysez pas.                                  |
| `code`       | string   | Le code stable, lisible par une machine, comme `permission_denied`. Voir les [codes d’erreur](#codes-derreur).                                                                                  |
| `permission` | string   | La clé d’[autorisation](/fr/reference/glossary/#permission) manquante, sur `permission_denied` et sur `escalation_denied` quand une seule autorisation manque.                                  |
| `helpers`    | string[] | Jusqu’à deux membres qui détiennent l’autorisation manquante, Propriétaires d’abord, pour qu’une personne sache à qui s’adresser.                                                              |
| `errors`     | object[] | Pour les requêtes non valides : une entrée par problème, avec `message`, `location` (comme `body.email` ou `query.pageSize`) et `value`.                                                       |
| `meta`       | object   | Des détails supplémentaires pour certains codes, par exemple `lockedUntil` et `failures` sur `locked`, `attemptsLeft` sur les erreurs de connexion, `retryAfter` sur les limites de débit des boutiques, `rules` sur `approval_required`, `version` et `startedAt` sur `maintenance`, `reference` sur `internal_error`, `reason` sur `store_cannot_create`, `automations` sur `pool_in_use`. |

`type` et `instance` appartiennent au modèle RFC 9457, mais ReputeCast les omet. Sans `type`, le type de problème est
`about:blank`, ce qui signifie que l’état HTTP dit tout. Quelques erreurs que le framework produit lui-même n’ont pas
de `code` : utilisez `status` pour celles-ci.

Une erreur serveur inattendue répond `500` avec le code `internal_error` et une référence dans `meta.reference`, comme
`err_7KQ2M4XA`, jamais avec le texte de l’erreur elle-même. Le serveur journalise l’erreur sous cette référence avec
l’ID de requête : un exploitant la retrouve donc en cherchant la référence dans les journaux.

Les chemins inconnus sous `/api/` répondent `404` avec le code `not_found` et le détail « No such API endpoint. »

## Exemples de corps

### Autorisation manquante

Une clé ou un membre sans l’autorisation que nécessite une opération reçoit `403`. Le `detail` indique ce que
l’appelant ne peut pas faire et qui peut l’aider, jamais la clé ; la clé est dans `permission`, et jusqu’à deux
membres qui la détiennent (Propriétaires d’abord, puis Admins) sont dans `helpers` :

```json title="403 Forbidden"
{
  "title": "Forbidden",
  "status": 403,
  "detail": "Sending needs a permission you don't have. Ask Marcus Chen or Linh Nguyen.",
  "code": "permission_denied",
  "permission": "campaigns:send",
  "helpers": ["Marcus Chen", "Linh Nguyen"]
}
```

Créez une clé qui détient l’autorisation, ou demandez à l’une des personnes listées dans `helpers`. Une clé n’a jamais
plus d’autorisations que le membre qui l’a créée (voir
[authentification et clés API](/fr/developers/api-authentication/)).

### Requête non valide

Un paramètre ou un champ du corps qui enfreint le schéma répond `422`, avec une entrée par problème dans `errors`. Les
requêtes mal formées, comme un JSON qui ne s’analyse pas, répondent `400` avec le même code.

```json title="422 Unprocessable Entity"
{
  "title": "Unprocessable Entity",
  "status": 422,
  "detail": "validation failed",
  "errors": [{ "message": "expected number <= 100", "location": "query.pageSize", "value": 500 }],
  "code": "validation_failed"
}
```

Les contrôles que fait ReputeCast lui-même placent la phrase dans `detail` et le champ dans `errors`, par exemple
`"detail": "Use a work email."` avec `"location": "body.email"`.

### Limite de débit atteinte

Au-delà du débit de requêtes par clé, l’API répond `429` avec un en-tête `Retry-After` :

```json title="429 Too Many Requests"
{
  "code": "rate_limited",
  "detail": "Rate limit reached. Requests resume within a minute; batch endpoints accept up to 1,000 items per call.",
  "status": 429,
  "title": "Too Many Requests"
}
```

Les « 1,000 items » de ce message valent pour l’ajout d’adresses à la liste de suppression ; l’opération d’envoi
transactionnel par lots accepte jusqu’à 100 messages. Attendez le nombre de secondes indiqué dans `Retry-After`, puis
renvoyez la requête. [Limites de débit](/fr/developers/api-rate-limits/) liste toutes les limites.

## Langue de `detail`

Les phrases que ReputeCast écrit dans `detail` (comme les autorisations manquantes, les problèmes de connexion, les
éléments introuvables et ses propres contrôles de validation) sont dans la langue de la requête quand ReputeCast la
connaît (`en` ou `vi`, et depuis la version 1.4.0, aussi `de`, `es` et `fr`) : la langue que demande l’en-tête
`Accept-Language`, sinon la langue de l’application du membre connecté, sinon l’anglais. Les clés API reçoivent
l’anglais, sauf si vous envoyez l’en-tête. Ce qu’écrit le framework reste en anglais, comme `validation failed` et les
messages de `errors` tels que `expected number <= 100`. Avec `Accept-Language: vi`, le détail d’une campagne introuvable
est `Không tìm thấy chiến dịch.`, et celui d’une autorisation manquante est par exemple :

```json title="403 Forbidden, Accept-Language: vi"
{
  "title": "Forbidden",
  "status": 403,
  "detail": "Bạn chưa có quyền quản lý khóa API. Hãy hỏi Marcus Chen hoặc Linh Nguyen.",
  "code": "permission_denied",
  "permission": "apikeys:manage",
  "helpers": ["Marcus Chen", "Linh Nguyen"]
}
```

`code`, `permission` et les autres champs ne changent jamais avec la langue.

## Gérer les erreurs

- Basez-vous sur `status` et `code`. Traitez `detail` comme un texte destiné à une personne.
- `401` : la clé est absente, inconnue, révoquée ou expirée. Corrigez la clé ; réessayer n’y change rien.
- `403` : une autorisation manque (`permission_denied`), l’opération nécessite une personne connectée
  (`humans_only`), la clé est appelée en dehors de ses
  [IP autorisées](/fr/developers/api-authentication/#limiter-une-clé-à-des-ip-autorisées) (`ip_not_allowed`), ou une
  clé d’intégration a appelé une opération que son intégration n’utilise pas (`integration_operation_denied`).
- `404`, `409`, `410`, `422` : corrigez la requête. Les codes `409` comme `version_conflict` et
  `idempotency_key_reused` indiquent ce qui a changé.
- `429` : attendez `Retry-After`. Pour les envois transactionnels, réessayez avec le même `Idempotency-Key` pour qu’un
  message ne soit envoyé qu’une fois (voir
  [envoyer des e-mails transactionnels avec l’API](/fr/developers/transactional-api/)).
- `502` et `503` : un service externe ou une partie du serveur n’a pas répondu. Réessayez avec un délai croissant.
- `503` avec `maintenance` : le serveur est en cours de mise à niveau et attend ses migrations de base de données. Les
  lectures fonctionnent toujours ; réessayez une modification après `Retry-After` (30 secondes).

Les [SDK clients](/fr/developers/sdks/#gérer-les-erreurs) transforment chaque problème en exception (une erreur en Go)
qui porte ces champs, et réessaient `429`, `502`, `503` et `504` quand une répétition est sans risque.
