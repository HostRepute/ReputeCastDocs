Chaque [instance](/fr/reference/glossary/#instance) ReputeCast sert une API REST de newsletter sous `/api/v1` à sa
propre URL publique, décrite par un document OpenAPI 3.1 que le serveur génère à partir de son code. Les personnes,
les [clés API](/fr/reference/glossary/#api-key) et les [agents MCP](/fr/reference/glossary/#mcp-agent) passent tous
le même contrôle d’[autorisation](/fr/reference/glossary/#permission) : une clé peut donc faire ce que ses
autorisations permettent, et rien de plus. Les erreurs sont des documents de problème RFC 9457 avec un `code` stable.

## Comment fonctionne une requête

1. Votre code appelle `https://<public URL>/api/v1/…` avec l’en-tête `Authorization: Bearer <key>`. Les opérations
   sur un [espace de travail](/fr/reference/glossary/#workspace) prennent son slug dans le chemin, par exemple
   `/api/v1/workspaces/acme-newsletter/campaigns`.
2. ReputeCast recherche la clé par son hash, la refuse avec `401` quand elle est inconnue, révoquée ou expirée, et
   limite ses autorisations à celles que détient, à ce moment-là, le membre qui l’a créée.
3. L’autorisation de l’opération (`x-permission` dans le document OpenAPI) est vérifiée. Quand elle manque, la réponse
   est `403`, avec la clé d’autorisation dans `permission` et jusqu’à deux membres qui la détiennent dans `helpers` ;
   la phrase `detail` nomme ces membres, pas la clé.
4. La réponse est du JSON (`application/json`), ou un document de problème (`application/problem+json`) quand l’appel
   échoue. Les réponses portent les en-têtes `X-RateLimit-*` (voir [limites de débit](/fr/developers/api-rate-limits/))
   et `X-ReputeCast-Version`, la version qu’exécute le serveur.

[Faire votre premier appel d’API](/fr/developers/api-quickstart/) déroule ces étapes avec `curl`, et
[authentification et clés API](/fr/developers/api-authentication/) décrit les clés en détail.

## Obtenir le document OpenAPI

Votre instance publie son document OpenAPI sans authentification, sous quatre formes :

| Chemin                  | Format             |
| ----------------------- | ------------------ |
| `/api/openapi.json`     | OpenAPI 3.1, JSON  |
| `/api/openapi.yaml`     | OpenAPI 3.1, YAML  |
| `/api/openapi-3.0.json` | OpenAPI 3.0, JSON  |
| `/api/openapi-3.0.yaml` | OpenAPI 3.0, YAML  |

La commande `reputecast openapi` affiche le même document sans base de données ni fichier de configuration (`--yaml`
pour du YAML) : vous pouvez donc le générer en CI à partir de la version que vous exécutez :

```sh title="Terminal"
curl -o reputecast-openapi.json https://reputecast.example.com/api/openapi.json
reputecast openapi --yaml > reputecast-openapi.yaml
```

À savoir sur ce document :

- Il décrit toutes les opérations du serveur, y compris celles que seule l’application web appelle avec une session
  connectée (connexion, sécurité du compte, administration de l’instance). La [référence de l’API](/api/) de ce site ne
  liste que les opérations qu’une clé API peut appeler.
- Chaque opération a un `operationId` (comme `list-campaigns`), un tag et trois extensions : `x-access` (qui peut
  l’appeler : `workspace`, `key`, `user`, `instance_admin` ou `public`), `x-permission` (la clé d’autorisation
  nécessaire) et, sur les opérations que seules les intégrations appellent, `x-integration`.
- Il n’a pas d’entrée `servers` : donnez à votre client l’URL publique de votre instance comme URL de base.
- Votre instance sert aussi sa propre référence de l’API à `/api/reference`, sans authentification : une page avec
  toutes les opérations de la version qu’elle exécute, groupées par tag, avec l’autorisation que chacune nécessite.
  Les liens de l’application vers la référence de l’API l’ouvrent. La [référence de l’API](/api/) de ce site ajoute
  les paramètres, les corps et les réponses de chaque opération, pour les opérations qu’une clé API peut appeler
  dans la version que décrit cette documentation.

## Générer un client

Tout générateur OpenAPI peut lire le document 3.1. Utilisez les variantes 3.0 avec les générateurs qui ne lisent
qu’OpenAPI 3.0. L’application web de ReputeCast génère ses propres types TypeScript avec
[openapi-typescript](https://openapi-ts.dev/cli) (vérifié en octobre 2026), qui lit le document depuis une URL :

```sh title="Terminal"
npx openapi-typescript https://reputecast.example.com/api/openapi.json -o reputecast.d.ts
```

La plupart des générateurs nomment les méthodes d’après l’`operationId` : `list-campaigns` devient ainsi une méthode
`listCampaigns` ou équivalente.

## Appeler l’API depuis votre serveur

Les clés API sont des secrets : appelez donc l’API depuis votre backend, une tâche planifiée ou un outil
d’automatisation, jamais depuis une page web. Les chemins `/api/` n’envoient aucun en-tête CORS, et le serveur refuse
les requêtes de navigateur intersites qui modifient des données. Pour recueillir des inscriptions sur un site web,
intégrez plutôt un [formulaire d’inscription](/fr/forms/signup-forms/) : ses endpoints acceptent les requêtes des
sites que vous autorisez.

## Valeurs par défaut et limites

<LimitsTable area="api" />

Les débits de requêtes ont leur propre page : [limites de débit](/fr/developers/api-rate-limits/). La façon dont
chaque opération de liste pagine ses résultats est décrite dans [pagination](/fr/developers/api-pagination/).

## Quand les modifier

Ces limites sont fixes. Parcourez les longues listes avec les paramètres de pagination de chaque opération, utilisez
les opérations par lots pour les traitements en masse, et envoyez les fichiers par les opérations d’import plutôt que
dans un corps JSON. Les exploitants du serveur peuvent modifier le nombre de requêtes par minute qu’une clé peut faire
avec `http.rate_limit_api` (voir la [référence de configuration](/fr/reference/configuration/)).
