Cette page liste les types d’événements webhook auxquels un endpoint de <UiPath path="nav.settings > settings.webhooks" /> peut s’abonner, et l’enveloppe qu’utilise chaque livraison. [Recevoir des webhooks](/fr/developers/webhooks/) montre comment créer un endpoint et vérifier les signatures.

## Enveloppe

Chaque livraison est un `POST` avec un corps JSON de cinq champs :

| Champ        | Valeur                                                                                        |
| ------------ | --------------------------------------------------------------------------------------------- |
| `id`         | L’ID de l’événement (UUID). Chaque endpoint qui reçoit l’événement reçoit le même ID ; servez-vous-en pour ignorer les doublons. |
| `type`       | Le type d’événement, par exemple `email.bounced`.                                             |
| `created_at` | Le moment où l’événement s’est produit, en UTC (RFC 3339).                                    |
| `workspace`  | Le slug de l’espace de travail.                                                               |
| `data`       | Le payload de l’événement. Sa forme dépend du type ; six événements qu’utilisent les intégrations ont un exemple de payload dans leur ligne ci-dessous. |

Tester un endpoint envoie un événement `webhook.test` :

```json title="webhook.test"
{
  "id": "01934f6e-8b2a-7c3d-9e4f-5a6b7c8d9e0f",
  "type": "webhook.test",
  "created_at": "2026-10-22T09:30:00.482913Z",
  "workspace": "acme-newsletter",
  "data": {
    "message": "Test event from ReputeCast. Verify the signature, then answer 2xx."
  }
}
```

Un endpoint avec <UiPath path="webhooks.batchLabel" /> activé reçoit plutôt ses événements `email.*` sous forme de
livraisons `email.batch` : `data.count` indique combien d’événements elle contient, jusqu’à 100, et `data.events` les
liste, chacun dans l’enveloppe ci-dessus, dans l’ordre où ils se sont produits. On ne peut pas s’abonner à
`email.batch` seul. Voir
[recevoir les événements e-mail par lots](/fr/developers/webhooks/#recevoir-les-événements-e-mail-par-lots).

## En-têtes

| En-tête                  | Valeur                                                                                                                                 |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| `Content-Type`           | `application/json`                                                                                                                     |
| `User-Agent`             | `ReputeCast-Webhooks/<version>`                                                                                                        |
| `X-ReputeCast-Event`     | Le type d’événement.                                                                                                                   |
| `X-ReputeCast-Delivery`  | L’ID de livraison : un par endpoint et par événement, inchangé d’une nouvelle tentative à l’autre.                                     |
| `X-ReputeCast-Timestamp` | L’heure Unix, en secondes, de cette tentative.                                                                                         |
| `X-ReputeCast-Signature` | Le HMAC-SHA256 en hexadécimal minuscule de `<timestamp>.<raw body>`, avec pour clé le secret `whsec_…` complet. Rejetez les horodatages décalés de plus de 5 minutes. Pendant les 24 heures qui suivent le renouvellement d’un secret, deux signatures séparées par une virgule, celle du nouveau secret en premier ; acceptez l’une ou l’autre. |

## Livraison et nouvelles tentatives

- Une réponse `2xx` dans les 10 secondes compte comme une livraison réussie. Tout autre statut, un délai dépassé ou une erreur de connexion entraîne une nouvelle tentative.
- Un événement est tenté jusqu’à 8 fois, avec 1, 2, 4, 8, 30, 90 et 225 minutes d’attente entre les tentatives (environ six heures au total). Après le huitième échec, il passe dans la file des lettres mortes, d’où vous pouvez le rejouer.
- Un endpoint en pause continue de mettre les événements en file d’attente, lots compris ; quand vous le réactivez, les événements en attente sont livrés dans l’ordre.
- Un endpoint qui échoue pendant une heure, ou dont une livraison passe dans la file des lettres mortes, prévient les personnes qui gèrent les webhooks avec <UiPath path="notify.event.webhook_failing" />.
- L’événement `webhook.test` n’est tenté qu’une fois, sans nouvelle tentative.

## S’abonner aux événements

Un endpoint s’abonne à 1 à 40 entrées. Chaque entrée est un type d’événement exact (`email.bounced`), tous les événements d’un groupe (`email.*`, d’après la partie qui précède le premier point) ou tous les événements (`*`). `email.*` inclut `email.replied` et `email.received`, listés dans le groupe Réponses ci-dessous. Disponible à partir de la prochaine version après la 1.6.0.

Chaque événement nécessite l’autorisation de consultation des données qu’il transporte, et les événements qui transportent des contacts nécessitent l’accès à toutes les listes : s’abonner à un événement que vous ne pouvez pas voir renvoie `403 permission_denied`, et un endpoint se met lui-même en pause quand la personne pour qui il envoie perd cet accès. Voir [pour qui un endpoint envoie](/fr/developers/webhooks/#pour-qui-un-endpoint-envoie).
