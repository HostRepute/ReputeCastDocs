Pour mettre à niveau ReputeCast, vous remplacez l’image ou le binaire par une version plus récente et la laissez
appliquer ses migrations de base de données ; tout le reste (configuration, clé secrète, données) reste tel quel.

## De 1.8.0 à 1.8.1 ou 1.8.2

1.8.1 ajoute la migration `03670` : la date de la dernière réponse humaine, complétée depuis les réponses conservées,
hors spam, réponses automatiques et contacts effacés. Elle parcourt les réponses et verrouille `contacts` ; sauvegardez
d’abord et procédez en période creuse. Seules les réponses reçues dans ReputeCast comptent. Annuler cette migration
supprime la date. 1.8.2 n’ajoute aucune migration ; ses changements concernent la publication des paquets.

<Aside type="caution" title="Vérifiez les flux de réengagement existants">
  La mise à niveau ne réécrit ni les graphes enregistrés ni les versions en cours. Suspendez les anciens flux et
  vérifiez leurs exécutions. Recherchez `sunset-entered` et une étape de désabonnement de toutes les listes nommée
  « Stop broadcasts » : corriger seulement le tag peut activer cette étape destructive. Remplacez le flux par le
  nouveau modèle ou vérifiez et testez tout son brouillon. Terminer sur l’ancienne version conserve son comportement :
  examinez le changement de version ou retirez les exécutions concernées avec un motif d’audit. Ne réabonnez pas les
  contacts en masse et ne retirez pas le tag sunset pour le remettre ensuite.
</Aside>

Les nouveaux modèles écoutent `sunset` et se terminent après une interaction humaine ou 14 jours, sans changer le
consentement aux listes. Seule la règle Sunset arrête Broadcasts (30 jours par défaut) ; l’effacement facultatif reste
distinct. Un clic ou une réponse rétablit l’éligibilité liée à l’engagement, pas le consentement. Suivez la
[procédure complète de mise à niveau sunset](https://github.com/HostRepute/ReputeCast/blob/v1.8.2/docs/deploy/README.md#from-180-to-181)
et vérifiez la [politique de santé des listes](/fr/audience/list-health/) avant de reprendre un flux.

## Voir quelle version vous utilisez

Un [admin de l’instance](/fr/reference/glossary/#instance-admin) voit la version installée, la dernière version
publiée et ses notes de version sous <UiPath path="shell.userMenuInstanceAdmin > admin.instance" />, dans la carte
<UiPath path="admin.versionCard" />. En ligne de commande, `reputecast version` affiche la même chose :
`reputecast <version> (<commit>) <Go version>`.

- Le badge <UiPath path="admin.updateAvailable" /> apparaît quand la dernière version publiée est plus récente que la
  version installée. Les builds sans numéro de version publiée (comme `dev`) ne l’affichent jamais.
- Sous <UiPath path="admin.upgradeOnServer" />, la carte affiche la commande Docker Compose
  `cd /opt/reputecast && docker compose pull && docker compose up -d`. Remplacez `/opt/reputecast` par le dossier qui
  contient votre `docker-compose.yml`. Quand l’exploitant du serveur définit `updates.managed_by` (depuis la version
  1.5.0), la carte affiche à la place « Les mises à jour sont gérées par … » avec son nom : c’est lui qui décide quand
  l’instance passe à une nouvelle version
  ([paramètres que gère l’exploitant du serveur](/fr/self-hosting/configuration/#paramètres-que-gère-lexploitant-du-serveur)).
- L’interrupteur <UiPath path="admin.updateCheck" /> récupère la dernière version publiée sur `api.github.com` une fois
  par jour. La requête ne contient ni numéro de version ni ID d’instance ; c’est le seul appel sortant que ReputeCast
  fait de lui-même. Désactivez-le ici, ou définissez `updates.check: false` dans la
  [configuration](/fr/reference/configuration/) pour le désactiver sur toute l’instance (l’interrupteur est alors
  désactivé et verrouillé, ici et lors de la première connexion).

## Avant de commencer

- Lisez les [notes de version](/fr/reference/release-notes/) de chaque version entre la vôtre et la nouvelle, aussi
  disponibles sur la [page des versions GitHub](https://github.com/hostrepute/reputecast/releases).
- [Sauvegardez la base de données et la clé secrète](/fr/self-hosting/backups/). Les migrations modifient le schéma, et
  une sauvegarde est le moyen fiable de revenir en arrière.
- Prévoyez une courte interruption pendant le redémarrage de l’application. À l’arrêt (`SIGTERM`, un redéploiement),
  un worker ne récupère plus de nouvelle tâche et laisse 10 secondes aux tâches en cours pour se terminer ; un envoi
  s’arrête entre deux lots, le lot en cours étant envoyé et enregistré.

## Mettre à niveau

<Tabs syncKey="install">
<TabItem label="Docker Compose">

<Steps>

1. Allez dans le dossier qui contient votre `docker-compose.yml` et faites une sauvegarde :

   ```sh
   docker compose exec -T postgres pg_dump -U reputecast -d reputecast -Fc > reputecast-before-upgrade.dump
   ```

2. Si vous épinglez une version dans `.env` (`REPUTECAST_VERSION=v1.8.0`), remplacez-la par le tag de la nouvelle
   version. Les tags de l’image sont les tags des versions avec leur `v` initial, plus `latest`. Sans
   `REPUTECAST_VERSION`, le fichier Compose utilise `latest`.

3. Récupérez la nouvelle image et recréez le conteneur de l’application :

   ```sh
   docker compose pull && docker compose up -d
   ```

   L’image démarre avec `serve --auto-migrate` : elle applique donc les migrations en attente avant de servir des
   requêtes. Les journaux affichent une ligne `migration applied` par migration, et `docker compose ps` affiche `app`
   comme `healthy` dès qu’il est prêt.

</Steps>

</TabItem>
<TabItem label="Binaire">

<Steps>

1. Faites une sauvegarde (consultez [sauvegarder et restaurer](/fr/self-hosting/backups/)).

2. Téléchargez l’archive de votre plateforme et `checksums.txt` depuis la
   [page des versions](https://github.com/hostrepute/reputecast/releases), et vérifiez le téléchargement :

   ```sh
   sha256sum --ignore-missing -c checksums.txt
   ```

3. Arrêtez chaque processus ReputeCast, par exemple avec `sudo systemctl stop reputecast`.

4. Remplacez le binaire (par exemple `/usr/local/bin/reputecast`) par le nouveau.

5. Appliquez les migrations une fois, avec le même environnement que celui du service :

   ```sh
   reputecast migrate up
   ```

   La commande applique les migrations de ReputeCast, puis celles de la file des tâches, et se termine par
   `Database is up to date.`

6. Redémarrez chaque processus. Si vous exécutez [plusieurs rôles](/fr/self-hosting/scaling/), mettez-les tous à
   niveau vers la même version.

</Steps>

</TabItem>
</Tabs>

Sur Kubernetes, `helm upgrade` exécute les migrations dans un Job avant que les pods ne changent
([Kubernetes](/fr/deploy/kubernetes/#mettre-à-niveau)). Sur une plateforme d’hébergement, suivez les étapes de mise à
niveau de son [guide](/fr/deploy/overview/).

## Tant que des migrations sont en attente

Un processus dont la base de données n’a pas toutes les migrations dont il a besoin, comme un binaire remplacé avant
l’exécution de `reputecast migrate up`, n’y écrit pas :

- Les pages et l’API fonctionnent normalement en lecture, sauf ce qu’ajoutent les migrations en attente : depuis la
  version 1.8.0, sa lecture répond aussi `503` avec le code `maintenance`. L’application affiche le bandeau
  <UiPath path="shell.bannerMaintenance" /> avant toute modification.
- Les écritures répondent `503` avec le code `maintenance`. La connexion et la déconnexion fonctionnent toujours, et
  les webhooks des fournisseurs d’envoi sont toujours stockés.
- Les workers attendent, donc rien n’est envoyé.
- `/readyz` répond `503`, si bien qu’un répartiteur de charge ou un orchestrateur continue d’envoyer le trafic vers la
  version précédente.

Le processus vérifie de nouveau toutes les 5 secondes et reprend de lui-même dès que `reputecast migrate up`, ou le
`--auto-migrate` d’un autre processus, les a appliquées. Les onglets du navigateur restés ouverts pendant une mise à
niveau proposent <UiPath path="shell.bannerReload" /> pour charger la nouvelle version.

Les migrations détiennent un verrou dans PostgreSQL : quand plusieurs processus démarrent avec `--auto-migrate`, l’un
les applique pendant que les autres l’attendent (jusqu’à 15 minutes), si bien que chaque migration ne s’exécute qu’une
fois. Exécutez-les via une connexion directe ou en mode session, et non via PgBouncer en mode transaction.

## Mettre à niveau vers 1.8.0

La version 1.8.0 modifie ces éléments sur le serveur ; les [notes de version](/fr/reference/release-notes/#180) listent
le reste.

- **Ce qui est conservé.** La connexion IA de chaque espace de travail devient son premier compte de modèle, avec la
  même clé, les mêmes prix, le même plafond et le même usage, et son modèle devient celui par défaut de chaque
  fonctionnalité ; un test des outils réussi compte toujours. L’[assistant IA](/fr/integrations/ai-assistant/) et les
  [clés personnelles](/fr/integrations/ai-models/#clés-personnelles) restent désactivés jusqu’à ce qu’une personne
  disposant de `integrations:manage` les active.
- **Sauvegardez d’abord :** la base de données, la clé secrète et le dossier des fichiers
  ([sauvegarder et restaurer](/fr/self-hosting/backups/)). Revenir à la 1.7.0 demande cette sauvegarde ou les migrations
  descendantes ci-dessous.
- **7 nouvelles migrations** (`03630` à `03660`). Démarrez d’abord le nouveau binaire ou la nouvelle image : tant
  qu’elles n’ont pas tourné, il fonctionne en lecture seule, et les lectures de ce qu’elles ajoutent répondent `503`
  avec le code `maintenance` ([tant que des migrations sont en attente](#tant-que-des-migrations-sont-en-attente)).
  Exécutez ensuite `reputecast migrate up`, ou laissez `--auto-migrate` les lancer, et remplacez chaque processus de la
  1.7.0 : dès que la première migration est validée, les pages IA de la 1.7.0 échouent.
- **Verrous.** Les migrations ont pris de 1 à 6 secondes au total lors du test de mise à niveau en amont, mais elles
  verrouillent le journal d’activité de l’IA et, brièvement, les tables des utilisateurs et des espaces de travail. Avec
  2 millions de requêtes d’IA, les écritures dans le journal d’activité de l’IA ont attendu jusqu’à 2,8 secondes, ses
  lectures jusqu’à 1,5 seconde, et les connexions et autres modifications des personnes et des espaces de travail
  jusqu’à 1,5 seconde. Lancez-les à un moment calme, sans transaction longue ouverte : une migration qui en attend une
  fait attendre derrière elle toutes les requêtes sur ces tables.
- **Revenir à la 1.7.0** fait exception à la règle d’une version mineure
  ([revenir à la version précédente](#revenir-à-la-version-précédente)) : la 1.7.0 se déclare prête sur le schéma de la
  1.8.0, mais ses pages IA répondent `500`. Restaurez la sauvegarde, ou arrêtez chaque processus de la 1.8.0 et exécutez
  sept fois `reputecast migrate down` avec le binaire de la 1.8.0 avant de démarrer la 1.7.0. Cela supprime ce qui a été
  créé en 1.8.0 : les paramètres de l’assistant, les conversations et leur usage ; les serveurs MCP, leurs outils, les
  connexions des membres et les confirmations en attente, les jetons d’actualisation encore en attente de révocation
  n’étant jamais envoyés ; les clés personnelles et les modèles choisis par chaque membre ; et chaque compte de modèle
  après le premier d’un espace de travail, chaque modèle après le premier de ce compte et le modèle par défaut de chaque
  fonctionnalité. Les requêtes sur des clés personnelles comptent de nouveau dans le plafond de l’espace de travail. Un
  espace de travail dont le compte issu de la mise à niveau a été retiré récupère son plus ancien compte restant,
  déconnecté et sans clé, et un espace sans compte perd son plafond et les fonctionnalités qu’il avait désactivées. Les
  changements que la 1.8.0 a apportés au premier compte, comme son plafond ou une clé remplacée, sont conservés.
- **Workers et la file `ai_assistant`.** Les réponses de l’assistant tournent dans les processus qui ont le rôle
  `worker`, jusqu’à la moitié de `worker.concurrency` à la fois et au moins 10. Avec des rôles séparés, gardez un worker
  en marche : sans lui, les messages restent en file et échouent au bout de 30 minutes
  ([passer à l’échelle](/fr/self-hosting/scaling/#lassistant-ia)).
- **Une connexion PostgreSQL de plus par processus web.** Chaque processus qui a le rôle `web` garde une connexion hors
  de son pool pour faire `LISTEN` sur les événements des conversations : prévoyez-la dans `max_connections`, et
  connectez-vous directement ou via PgBouncer en mode session, pas en mode transaction
  ([PostgreSQL](/fr/self-hosting/postgres/#dimensionner-le-pool-de-connexions)).
- **Flux d’événements derrière un proxy.** Les réponses de l’assistant sont des Server-Sent Events : désactivez la mise
  en tampon, ne compressez pas `text/event-stream` et servez HTTP/2
  ([les flux d’événements de l’assistant](/fr/self-hosting/reverse-proxy/#les-flux-dévénements-de-lassistant)).
- **Serveurs MCP.** La connexion OAuth demande une URL publique en `https://` : les membres reviennent à
  `<URL publique>/api/v1/ai/mcp/oauth/callback`, et le document de métadonnées client de ReputeCast n’est servi que sous
  une URL en `https://` ([l’adresse de redirection OAuth](/fr/integrations/mcp-servers/#ladresse-de-redirection-oauth)).
  `providers.allow_private_networks` permet désormais aussi des serveurs MCP et leurs serveurs d’autorisation sur des
  adresses privées, comme il le faisait déjà pour les serveurs de modèles compatibles OpenAI
  ([configuration](/fr/self-hosting/configuration/#lassistant-ia)).

## Mettre à niveau vers 1.7.0

La version 1.7.0 modifie ces éléments sur le serveur ; les [notes de version](/fr/reference/release-notes/#170)
listent le reste.

- **26 nouvelles migrations** (`03490` à `03625`).
- **Requêtes IA longues.** Un [brouillon à partir d’une consigne](/fr/integrations/ai-drafts/) attend le modèle jusqu’à
  trois minutes. Si un reverse proxy interrompt les réponses plus tôt, augmentez son délai de lecture pour
  `/api/v1/workspaces/*/ai/drafts/*` ([requêtes IA longues](/fr/self-hosting/reverse-proxy/#requêtes-ia-longues)).
- **Prix de l’IA.** La migration `03600` marque comme inconnus les prix d’une connexion IA quand ils valaient tous deux
  0 sans venir de la grille de prix de ReputeCast. Ses fonctionnalités refusent alors les nouvelles requêtes jusqu’à ce
  qu’une personne disposant de `integrations:manage` définisse les deux prix, y compris 0 pour un modèle gratuit
  ([modèles d’IA](/fr/integrations/ai-models/#dépannage)).
- **Stockage objet, facultatif.** Les fichiers peuvent être conservés dans un bucket compatible S3 avec
  `storage.backend: s3` ; le dossier des fichiers reste la valeur par défaut
  ([stockage objet](/fr/self-hosting/object-storage/)).
- **`PORT`.** Sans `http.addr`, ReputeCast écoute sur `:$PORT` quand la plateforme le définit. L’image Docker définit
  `REPUTECAST_HTTP__ADDR=:8080` : les conteneurs ne sont donc pas concernés.
- **Proxys de confiance sur les plateformes.** `http.trusted_proxies: private` fait confiance au routeur de Render,
  Railway, Coolify, DigitalOcean ou d’un ingress Kubernetes ([reverse proxy et TLS](/fr/self-hosting/reverse-proxy/)).
- **Adresses réservées du site.** `/team`, `/resume`, `/comments`, `/track` et `/sponsor` appartiennent au site web de
  chaque espace de travail. Une page déjà placée à l’une de ces adresses sur un domaine personnalisé est masquée ;
  donnez-lui une autre adresse.

## Mettre à niveau vers 1.6.0

La version 1.6.0 modifie ces éléments sur le serveur ; les [notes de version](/fr/reference/release-notes/#160)
listent le reste.

- **9 nouvelles migrations** (`03450` à `03483`).
- **La réputation Postmaster disparaît.** Google Postmaster Tools v2 ne fournit plus de réputation de domaine ni d’IP :
  la migration `03460` supprime donc ces colonnes. Revenir à la 1.5.0 ne rétablit pas les valeurs.
- **GeoIP, facultatif.** Les rapports de campagne affichent les pays et les villes dès que `geoip.database` pointe vers
  un fichier que vous téléchargez et que vous redémarrez ([ajouter une base de données GeoIP](/fr/self-hosting/geoip/)).
  ReputeCast ne le télécharge jamais.
- **Les IP autorisées nécessitent la véritable adresse du client.** Les clés API et les agents MCP peuvent désormais
  être limités à des adresses et à des réseaux. Derrière un reverse proxy, définissez `http.trusted_proxies`, sinon
  chaque appel semble venir du proxy
  ([reverse proxy et TLS](/fr/self-hosting/reverse-proxy/#définir-lurl-publique-et-les-proxys-de-confiance)).
- **Le fichier Compose accompagne chaque version.**
  `https://github.com/hostrepute/reputecast/releases/latest/download/docker-compose.yml` correspond toujours à l’image
  la plus récente ([installer avec Docker Compose](/fr/self-hosting/docker/)).

## Mettre à niveau vers 1.5.0

La version 1.5.0 corrige ce qu’un audit de sécurité a relevé
([sécurité et durcissement](/fr/self-hosting/security/#comment-reputecast-protège-vos-données)) et modifie ces éléments
sur le serveur ; les [notes de version](/fr/reference/release-notes/#150) listent le reste.

- **10 nouvelles migrations** (`03400` à `03446`).
- **URL de rappel WhatsApp.** L’URL de rappel de chaque compte WhatsApp se termine désormais par son propre jeton,
  `<public URL>/hooks/whatsapp/<workspace>/<token>`. Un compte connecté auparavant garde son ancienne adresse jusqu’à
  ce que Meta appelle la nouvelle : rien ne s’arrête donc à la mise à niveau. Pour le faire passer à la nouvelle
  adresse, ouvrez <UiPath path="nav.providers > channels.whatsapp > whatsapp.tabAccount" /> :
  <UiPath path="whatsapp.oldAddressTitle" /> affiche la nouvelle URL de rappel. Dans Meta for Developers › votre app ›
  WhatsApp › Configuration, collez-la comme Callback URL (le jeton de vérification ne change pas) et choisissez
  **Verify and save**. Dès le premier appel de Meta à la nouvelle URL, l’ancienne adresse refuse les livraisons du
  compte. Revenir à la 1.4 après ce changement impose de recoller l’ancienne adresse dans Meta
  ([WhatsApp](/fr/channels/whatsapp/#lurl-de-rappel)).
- **AWS End User Messaging (SMS).** Les messages SNS ne sont acceptés que s’ils viennent de la propre rubrique d’un
  fournisseur. Un fournisseur dont le webhook a été configuré à la main dans AWS conserve la rubrique d’où venaient
  ses événements vérifiés. S’ils venaient de plusieurs rubriques, ou si aucun n’est encore arrivé, ses accusés de
  réception et ses réponses sont refusés jusqu’à ce que SNS confirme de nouveau l’abonnement : dans la console SNS,
  supprimez l’abonnement HTTPS à l’adresse de ReputeCast et recréez-le. Les connexions Amazon SES avaient déjà leur
  rubrique.
- **Domaines de deux espaces de travail.** Un domaine personnalisé, un domaine de liens courts SMS ou un domaine de
  suivi des liens qu’un autre espace de travail a vérifié en premier, ou un domaine sous l’hôte propre de l’URL
  publique, nécessite désormais l’enregistrement TXT `_reputecast.<domain>` de cet espace de travail. Les domaines
  vérifiés sont de nouveau contrôlés dans les 30 minutes qui suivent la mise à niveau
  ([domaines personnalisés](/fr/self-hosting/reverse-proxy/#domaines-personnalisés)).
- **Secrets enregistrés.** Changer la destination d’un secret enregistré, comme un hôte SMTP ou un émetteur SSO,
  nécessite de saisir de nouveau le secret.
- **Deux paramètres facultatifs** pour une instance que vous exploitez pour le compte d’autrui,
  `http.public_url_locked` et `updates.managed_by`
  ([paramètres que gère l’exploitant du serveur](/fr/self-hosting/configuration/#paramètres-que-gère-lexploitant-du-serveur)).

## Mettre à niveau vers 1.3.0

La version 1.3.0 modifie ces éléments sur le serveur ; les [notes de version](/fr/reference/release-notes/#130)
listent le reste.

- **23 nouvelles migrations** (`03360` à `03388`) ; certaines construisent des index en mode concurrent. L’une crée
  l’extension `pg_trgm` pour la recherche de contacts, que le propriétaire de la base de données peut créer
  ([PostgreSQL](/fr/self-hosting/postgres/#postgresql-managé)).
- **`delivery_events` passe en partitions mensuelles.** Après les migrations, `migrate up` et `serve --auto-migrate`
  convertissent la table de chaque envoi, livraison, rebond, ouverture et clic, sauf si
  `reputecast migrate partition-events` l’a déjà fait. Rien n’est copié et les écritures continuent, mais deux étapes
  lisent toute la table : sur une très grande table, exécutez d’abord vous-même `reputecast migrate partition-events`,
  à une heure calme ([partitions mensuelles](/fr/self-hosting/postgres/#partitions-mensuelles-de-delivery_events)).
- **Lecture seule jusqu’à la migration, et migrations verrouillées**, comme décrit
  [plus haut](#tant-que-des-migrations-sont-en-attente).
- **`/metrics` a été déplacé** vers son propre écouteur, `:9464`. Si Prometheus collectait sur le port principal,
  faites-le pointer vers 9464 ou définissez `metrics.token`
  ([vérifications de l’état, métriques et journaux](/fr/self-hosting/monitoring/)).
- **Une vérification de l’état du conteneur.** L’image exécute `reputecast healthcheck`, si bien que Docker signale
  l’application comme `healthy` dès que `/readyz` répond.
- **Des limites de débit par session de navigateur.** Chaque navigateur connecté dispose de ses propres 600 requêtes
  par minute ; les navigateurs derrière une même adresse en partagent 6 000
  ([sécurité et durcissement](/fr/self-hosting/security/)).
- **nginx avec HTTP/2.** L’[exemple nginx](/fr/self-hosting/reverse-proxy/) active désormais HTTP/2, ce qui charge
  l’application beaucoup plus vite sur les téléphones.

## Mettre à niveau vers 1.2.0

La version 1.2.0 modifie ces éléments sur le serveur ; les [notes de version](/fr/reference/release-notes/#120)
listent le reste.

- **45 nouvelles migrations** (`03000` à `03350`) s’exécutent au premier démarrage, ou avec `reputecast migrate up`.
  Trois index sur les tables `contacts` et `messages` sont construits en mode concurrent, pour que les imports, les
  inscriptions et les envois continuent pendant leur construction sur une grande base de données.
- **Un seul nom pour l’URL publique.** `REPUTECAST_PUBLIC_URL` définit désormais `http.public_url` pour toutes les
  façons d’exécuter ReputeCast, binaire compris, et le `docker-compose.yml` fourni la transmet telle quelle à
  l’application. `REPUTECAST_HTTP__PUBLIC_URL`, son ancien nom, fonctionne toujours quand `REPUTECAST_PUBLIC_URL`
  n’est pas défini.
- **Des requêtes DNS pour les fournisseurs de messagerie.** ReputeCast identifie le fournisseur de messagerie d’un
  contact à partir des enregistrements MX de son domaine, si bien que Google Workspace compte comme Gmail et
  Microsoft 365 comme Outlook. Après la mise à niveau, un balayage d’arrière-plan toutes les 2 minutes interroge les
  domaines d’entreprise des contacts existants. Le serveur a besoin d’un résolveur fonctionnel : celui du système, ou
  les serveurs de `dns.servers` ([référence de la configuration](/fr/reference/configuration/)). Un domaine pas encore
  interrogé compte comme Autre.
- **Les liens de rapports partagés expirent.** Les liens de rapports en lecture seule créés avant la 1.2.0
  n’expiraient jamais ; chacun de ceux qui fonctionnent encore expire désormais 30 jours après la mise à niveau.
- **Des règles de réponse par défaut.** Les espaces de travail qui n’ont aucune règle de réponse propre reçoivent les
  règles de réponse par défaut des fournisseurs de messagerie sous
  <UiPath path="nav.providers > providers.tabTraffic" /> (consultez
  [les règles de trafic](/fr/providers/traffic-rules/)).

## Vérifier le résultat

- <UiPath path="admin.versionCard" /> affiche la nouvelle version comme installée.
- `reputecast migrate status` liste chaque migration avec une date d’application et aucune en `pending`. Dans
  Docker : `docker compose exec app /usr/local/bin/reputecast migrate status`.
- `/readyz` répond `ready` ([vérifications de l’état, métriques et journaux](/fr/self-hosting/monitoring/)), et
  `reputecast doctor` indique le schéma comme `current`.

## Revenir à la version précédente

Revenir à l’image ou au binaire précédent n’annule pas les migrations : la base de données conserve le schéma plus
récent. Au sein d’une version mineure (de 1.3.0 à 1.3.2), les migrations ne font qu’ajouter, et sur une version
mineure d’écart (de 1.3 à 1.2), l’ancien binaire fonctionne sur le schéma plus récent. Lisez d’abord les notes de
version : une version qui supprime ou renomme quelque chose l’indique. La 1.8.0 en fait partie : revenir à la 1.7.0
demande la sauvegarde, ou sept migrations descendantes qui suppriment ce que la 1.8.0 a créé
([mettre à niveau vers 1.8.0](#mettre-à-niveau-vers-180)). Pour remonter plus loin, restaurez la sauvegarde.

- **Restaurez la sauvegarde** pour retrouver exactement l’état d’avant la mise à niveau : arrêtez ReputeCast,
  restaurez le dump effectué (consultez [restaurer](/fr/self-hosting/backups/#restaurer)), puis démarrez la version que
  vous utilisiez auparavant. Les modifications faites après la mise à niveau sont perdues.
- **Épinglez la version précédente** (`REPUTECAST_VERSION` dans `.env`, puis `docker compose up -d`), comme le
  suggère la carte <UiPath path="admin.versionCard" />, quand vous voulez conserver les données écrites depuis la mise
  à niveau. La 1.2 fonctionne aussi avec la table `delivery_events` partitionnée. Revenir de la 1.6 à la 1.5 laisse
  vides la réputation de domaine et d’IP de Postmaster, puisque la migration `03460` l’a supprimée ; les comptes
  WhatsApp passés à leur nouvelle URL de rappel ont besoin de l’ancienne dans Meta pour fonctionner de nouveau en 1.4.
- `reputecast migrate down` annule uniquement la dernière migration de ReputeCast, une par exécution, et ne touche pas
  aux tables de la file des tâches. Elle est destinée au développement : les migrations descendantes suppriment des
  données, ne l’exécutez donc pas sur une base de données de production, sauf pour revenir de la 1.8.0 à la 1.7.0
  ([mettre à niveau vers 1.8.0](#mettre-à-niveau-vers-180)).

## Dépannage

- **Le nouveau conteneur s’arrête au démarrage** : lisez `docker compose logs app`. Une migration en échec arrête le
  démarrage avec `migrate: …` ; restaurez la sauvegarde et signalez l’erreur avec la version concernée.
- **L’application reste unhealthy et `/readyz` répond `database schema behind this release`** : aucun processus n’a
  appliqué les migrations. Exécutez `reputecast migrate up`, ou démarrez un processus avec `--auto-migrate`.
- **`migrate: another migrator held the lock for 15m0s`** : un autre processus était encore en train de migrer, par
  exemple en convertissant une grande table `delivery_events`. Laissez-le terminer, puis redémarrez celui-ci.
- **La carte de version indique que la vérification des mises à jour a échoué** : le serveur ne peut pas joindre
  `api.github.com`, ou GitHub a répondu par une erreur. Rien d’autre n’est affecté ; la vérification suivante a lieu
  le lendemain.
- **La dernière version publiée affiche un tiret** : la vérification est désactivée, ou n’a pas encore été exécutée.
