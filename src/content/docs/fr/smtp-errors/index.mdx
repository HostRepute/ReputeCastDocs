Cette référence liste les codes d’erreur SMTP que les fournisseurs de messagerie renvoient le plus souvent aux
expéditeurs de newsletters, la signification de chacun et la [classe de rebond](/fr/reference/glossary/#bounce-class)
que lui donne ReputeCast. Chaque code renvoie vers une page avec le texte officiel du serveur de réception, la cause et
la correction.

## Codes

<TableScroll label="Codes d’erreur SMTP par fournisseur de messagerie">

| Code                                                                  | Fournisseur de messagerie            | Signification                                                                                                            | Classe de rebond ReputeCast                  |
| --------------------------------------------------------------------- | ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------- |
| [421 4.7.28](/fr/smtp-errors/gmail-421-4-7-28/)                       | Gmail                                | Gmail a constaté un volume inhabituel d’e-mails depuis votre adresse IP, votre domaine ou les domaines de vos liens, et le limite pour l’instant. | `spam_block`                 |
| [550 5.7.26](/fr/smtp-errors/gmail-550-5-7-26/)                       | Gmail                                | Le message a échoué à SPF et à DKIM, ou à la politique DMARC du domaine From, et a été bloqué.                          | `policy_block`                               |
| [550 5.7.1](/fr/smtp-errors/gmail-550-5-7-1/)                         | Gmail                                | Le message a été bloqué comme probablement non sollicité, pour la faible réputation de l’adresse IP ou du domaine d’envoi, ou par politique. | `spam_block`, `reputation` ou `policy_block` |
| [550 5.1.1](/fr/smtp-errors/gmail-550-5-1-1/)                         | Gmail                                | Le compte de messagerie n’existe pas.                                                                                    | `mailbox_unknown`                            |
| [452 4.2.2](/fr/smtp-errors/gmail-452-4-2-2/)                         | Gmail                                | La boîte de réception du destinataire n’a plus d’espace de stockage.                                                     | `mailbox_full`                               |
| [550 5.7.515](/fr/smtp-errors/outlook-550-5-7-515/)                   | Outlook.com, Hotmail, Live.com, MSN  | Le domaine From ne respecte pas les exigences d’authentification de Microsoft pour les expéditeurs de gros volumes.     | `policy_block`                               |
| [421 4.7.0 \[TSS04\]](/fr/smtp-errors/yahoo-421-4-7-0-tss04/)         | Yahoo                                | Yahoo a différé les messages à cause des plaintes, du contenu, de la réputation de l’IP ou d’un trafic inhabituel.       | `reputation`                                 |
| [Compte en cours d’examen](/fr/smtp-errors/amazon-ses-under-review/)  | Aucun : Amazon SES est un fournisseur d’envoi | Pas une réponse SMTP. </TableScroll>

La classe dépend du texte du serveur de réception autant que du code : un même code peut donc relever de plusieurs
classes. Chaque page liste les variantes.

Pendant un envoi, les [règles de réponse](/fr/reference/glossary/#reply-rule) agissent sur les réponses elles-mêmes,
avant tout seuil de taux. Chaque espace de travail démarre avec des règles pour `TSS04` et `TS04` de Yahoo, `S3150`
d’Outlook et `421-4.7.28` de Gmail ; voir [définir les règles de trafic](/fr/providers/traffic-rules/). Les rebonds de
blocage/politique et les reports ont chacun leurs propres seuils par fournisseur de messagerie ; voir
[suivre un envoi et la pause automatique](/fr/campaigns/live-monitor/).

## Lire une réponse SMTP

Une réponse SMTP commence par un code de réponse à trois chiffres (`550`), généralement suivi d’un code d’état étendu
(`5.7.26`) et du texte du serveur de réception. Un premier chiffre 4 signale un échec temporaire : le fournisseur d’envoi
garde le message et réessaie plus tard. Un premier chiffre 5 signale un échec permanent : le fournisseur d’envoi cesse
ses tentatives. Les codes de réponse sont définis dans la [RFC 5321](https://www.rfc-editor.org/rfc/rfc5321#section-4.2)
et les codes d’état étendus dans la [RFC 3463](https://www.rfc-editor.org/rfc/rfc3463) (vérifié en octobre 2026).

## Retrouver le code d’origine d’un rebond

ReputeCast conserve le type d’événement, le code et le texte d’origine de chaque fournisseur d’envoi à côté de
l’[événement normalisé](/fr/reference/glossary/#normalized-event) : vous pouvez donc toujours voir ce qu’a dit le serveur
de réception.

### Dans un rapport de campagne

<Steps>

1. Ouvrez <UiPath path="nav.campaigns" /> puis le <UiPath path="campaigns.report" /> de la campagne.
2. Repérez le tableau des rebonds. Chaque ligne correspond à un type de rebond (la colonne
   <UiPath path="reports.colType" />). <UiPath path="reports.colCodes" /> liste le fournisseur d’envoi, son propre type
   d’événement et le code d’origine, du plus fréquent au moins fréquent, par exemple `SES Permanent/General 550 5.1.1`.
3. Lisez <UiPath path="reports.colSuppression" /> pour voir ce qu’il advient des adresses (voir
   [classes de rebond dans le rapport](#classes-de-rebond-dans-le-rapport)).
4. Là où la colonne affiche <UiPath path="reports.review" />, sélectionnez-le pour lire ce qu’a dit chaque fournisseur
   d’envoi. Les adresses ne figurent pas dans cette vue.

</Steps>

Le tableau des rebonds ne compte que les rebonds définitifs et temporaires. Les reports délivrés lors d’une tentative
ultérieure n’y apparaissent pas. [Lire les rapports de campagne](/fr/campaigns/reports/) explique les autres tableaux.

### Pour une adresse ou un message

<Steps>

1. Ouvrez <UiPath path="nav.providers > providers.tabEvents" />.
2. Dans le journal des événements, filtrez par <UiPath path="providers.events.typeFilter" /> (par exemple
   <UiPath path="providers.events.optionDeferred" />, <UiPath path="providers.events.optionHardBounce" /> ou
   <UiPath path="providers.events.optionSoftBounce" />), ou recherchez le destinataire ou l’ID du message.
3. Lisez la colonne <UiPath path="providers.events.colCode" /> : le code et le texte du serveur de réception.

</Steps>

Le journal des événements conserve les événements pendant 90 jours. Son export CSV ajoute les colonnes
`original_code`, `diagnostic` et `bounce_class` ; les destinataires sont masqués sauf si vous avez
`subscribers:export`, et chaque export est consigné dans le journal d’audit.
[Événements de livraison et synchronisation des suppressions](/fr/providers/events-and-sync/) explique comment les
événements arrivent.

Les adresses de la liste de suppression gardent aussi leur code :
<UiPath path="nav.audience > audience.tabSuppressions" />, colonne
<UiPath path="audience.suppressions.colReason" />.

## Classes de rebond dans le rapport

Chaque adaptateur fait correspondre le rebond de son fournisseur d’envoi à l’une des huit classes. Le rapport de
campagne les regroupe en lignes :

<TableScroll label="Classes de rebond dans le rapport">

| Classe de rebond                           | Ligne du rapport                                      | Colonne <UiPath path="reports.colSuppression" />  |
| ------------------------------------------ | ----------------------------------------------------- | ------------------------------------------------- |
| `mailbox_unknown`                          | <UiPath path="reports.bounceType.unknownUser" />      | <UiPath path="reports.autoSuppressed" />          |
| `domain_invalid`                           | <UiPath path="reports.bounceType.domainInvalid" />    | <UiPath path="reports.autoSuppressed" />          |
| `mailbox_full`                             | <UiPath path="reports.bounceType.mailboxFull" />      | <UiPath path="reports.retryNext" />               |
| `temporary`                                | <UiPath path="reports.bounceType.deferralExpired" />  | <UiPath path="reports.retryNext" />               |
| `policy_block`, `spam_block`, `reputation` | <UiPath path="reports.bounceType.blocked" />          | <UiPath path="reports.investigate" />             |
| `other`                                    | <UiPath path="reports.bounceType.other" />            | <UiPath path="reports.review" />                  |

</TableScroll>

- Les deux lignes de rebonds définitifs montrent les adresses comme exclues. Si certaines ne sont pas encore sur la
  liste, la colonne propose de les ajouter.
- Les lignes de rebonds temporaires ne permettent pas d’exclure depuis le rapport : ces adresses reçoivent de nouveau des
  e-mails au prochain envoi. Vous pouvez toujours en ajouter une à la main sur la
  [liste de suppression](/fr/audience/suppressions/).
- La ligne des blocages concerne l’expéditeur, pas l’adresse : ses adresses ne sont donc jamais exclues pour ce motif.
  <UiPath path="reports.investigate" /> montre ce qu’a dit chaque fournisseur d’envoi, et
  <UiPath path="reports.retryTitle" /> crée de nouveau un brouillon du numéro pour ces adresses une fois la cause
  corrigée.

## Quand ReputeCast exclut une adresse

ReputeCast place une adresse sur la [liste de suppression](/fr/reference/glossary/#suppression-list) partagée, pour tous
les flux et tous les fournisseurs d’envoi, quand le fournisseur d’envoi signale un rebond définitif, une plainte ou un
désabonnement. Un blocage lié à la réputation ou à la politique de l’expéditeur n’exclut jamais l’adresse, même sous
forme de rebond définitif : l’adresse est valide. Un rebond temporaire ou un report n’exclut jamais une adresse à lui
seul. Les e-mails transactionnels ajoutent une règle : quand un message Transactionnel rebondit temporairement et que
l’adresse a eu 3 rebonds temporaires en 7 jours, l’adresse est exclue.

Une adresse qui n’existe pas (`mailbox_unknown`, `domain_invalid`) est un rebond définitif chez tous les fournisseurs
d’envoi. Un blocage permanent lié à l’expéditeur (`policy_block`, `spam_block`, `reputation`) est enregistré comme
indiqué ci-dessous. Dans les deux cas, il n’exclut pas l’adresse ; pendant un envoi, un rebond définitif compte dans le
seuil de rebonds de blocage/politique du fournisseur de messagerie, et un rebond temporaire dans son seuil de reports.

| Fournisseur d’envoi                                                  | Un blocage permanent lié à l’expéditeur est enregistré comme                                                                          |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Amazon SES, Resend                                                   | Un rebond définitif quand le fournisseur d’envoi indique le type de rebond `Permanent`, sinon un rebond temporaire                   |
| Postal                                                               | Un rebond définitif quand Postal indique `HardFail` avec une réponse 5xx, sinon un rebond temporaire                                  |
| SMTP (boîte de réception des rebonds)                                | Un rebond définitif quand l’état du rapport de rebond est `5.x.x`                                                                     |
| Postmark                                                             | Un rebond temporaire, sauf si Postmark le classe en `HardBounce`, `BadEmailAddress` ou `ManuallyDeactivated`                          |
| SendGrid                                                             | Un rebond temporaire quand SendGrid le marque comme bloqué ou le classe en Content, Reputation ou Frequency/Volume, sinon un rebond définitif |
| Mailjet                                                              | Un rebond temporaire quand Mailjet rattache l’erreur au spam, au contenu, à son système ou à Mailjet lui-même, sinon l’indicateur définitif ou temporaire de Mailjet |
| SparkPost                                                            | Un rebond temporaire : seules les classes de rebond 10 et 30 de SparkPost (destinataires non valides) sont définitives                 |
| Mailgun, Brevo, Azure Communication Services, adaptateur HTTP générique | Un rebond temporaire                                                                                                               |
| Adaptateurs communautaires                                           | Ce que l’adaptateur indique                                                                                                           |

Si une version antérieure a exclu des adresses bloquées comme rebonds définitifs et que vous avez corrigé la cause, vous
pouvez les retirer de la liste de suppression en indiquant un motif. Un contact retiré après un rebond définitif revient
en consentement en attente et a besoin d’un nouvel opt-in avant de recevoir de nouveau des e-mails.

## Comment ReputeCast choisit une classe de rebond

ReputeCast lit l’événement du fournisseur d’envoi et le texte du serveur de réception dans cet ordre. La première
correspondance l’emporte.

1. Le type de rebond propre au fournisseur d’envoi, quand il en a un précis (par exemple les sous-types `NoEmail` et
   `MailboxFull` d’Amazon SES, `InboxFull` et `DnsError` de Postmark, les classes de rebond de SparkPost).
2. Des mots du texte, comme `reputation`, `TSS04` ou `rate limited due to` pour `reputation`, et `spam`, `blocklist`,
   `Spamhaus`, `virus` ou `phish` pour `spam_block`.
3. Le code d’état étendu :

   | Code d’état étendu                                        | Classe de rebond  |
   | --------------------------------------------------------- | ----------------- |
   | 5.1.0, 5.1.1, 5.1.6, 5.2.1                                | `mailbox_unknown` |
   | 4.2.2, 5.2.2                                              | `mailbox_full`    |
   | 4.1.2, 5.1.2, 5.1.10, 4.4.4, 5.4.4                        | `domain_invalid`  |
   | 5.4.1, 5.7.0, 5.7.1, 5.7.23 à 5.7.27, 5.7.509, 5.7.606    | `policy_block`    |

4. D’autres mots, comme `user unknown` ou `does not exist` pour `mailbox_unknown`, `mailbox full` ou `over quota` pour
   `mailbox_full`, `domain not found` ou `no mx` pour `domain_invalid`, et `dmarc`, `spf`, `dkim`, `access denied` ou
   `policy` pour `policy_block`.
5. Toute autre réponse 4xx est `temporary` ; tout le reste est `other`.

Comme le texte est lu avant le code, le 421 4.7.28 de Gmail est `spam_block` : son texte dit « To protect our users from
spam ». Quand un fournisseur d’envoi ne transmet que le code, sans le texte, la classe peut être différente : 421 4.7.28
seul donne `temporary`, et 550 5.7.515 seul donne `other`.
