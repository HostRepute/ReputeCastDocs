Créez des modèles d’e-mails transactionnels dans le mode transactionnel de l’éditeur, déclarez les variables que
votre application envoie, et publiez une nouvelle version sans casser les appels que votre application fait déjà.

## Avant de commencer

- `transactional:edit` pour créer des modèles et enregistrer des brouillons ; `transactional:publish` pour les
  publier, revenir à une version antérieure, les archiver ou les supprimer. Les Éditeurs peuvent modifier ; la
  publication est une [autorisation sensible](/fr/reference/permissions/).
- Un expéditeur Transactionnel vérifié. Voir
  [ajouter des domaines d’envoi et des expéditeurs](/fr/providers/senders-and-domains/).
- Lisez [le fonctionnement de l’e-mail transactionnel](/fr/transactional/overview/) si les catégories et la route
  Transactionnel sont nouvelles pour vous.

## Créer un modèle

<Steps>

1. Ouvrez <UiPath path="nav.transactional > transactional.common.tabTemplates" /> et choisissez
   <UiPath path="transactional.common.newTemplate" />. Partez d’un modèle de départ (Réinitialisation du mot de passe,
   Lien de connexion, Vérification de l’adresse e-mail, Bienvenue, Reçu ou facture, Fin de l’essai, Invitation
   d’équipe, Alerte de consommation) ou d’un modèle vierge. Pour reprendre des modèles d’une autre plateforme,
   utilisez <UiPath path="transactional.common.importTemplates" /> (voir
   [importer des modèles transactionnels](/fr/migrate/transactional-templates/)).

2. Dans l’en-tête, définissez le nom, l’**ID** qu’appelle votre application (comme `password-reset`) et la
   catégorie. L’ID se compose de lettres minuscules, de chiffres et de traits d’union simples, 64 caractères au plus.
   Il est figé après la première publication ; pour utiliser un autre ID plus tard, dupliquez le modèle.

3. Rédigez l’**Objet** et le **Texte d’aperçu**. Les deux acceptent des variables
   [Liquid](/fr/campaigns/personalization/) comme `{{ expires_in }}`. L’aperçu de la boîte de réception, à côté, en
   fait le rendu avec les données de test sélectionnées.

4. Concevez le corps avec les mêmes blocs que l’[éditeur](/fr/campaigns/composer/), plus les blocs sous
   <UiPath path="composer.canvas.groupReputecast" /> : **En-tête + logo**, **Lignes du reçu** et
   **Pied de page transactionnel**. Les modèles essentiels reçoivent le pied de page transactionnel avec votre
   entreprise et votre adresse, sans lien de désabonnement ; les catégories facultatives reçoivent le pied de page de
   désabonnement.

   <Screenshot
     id="transactional-template"
     alt="Le modèle « Password reset » dans l’éditeur : ID password-reset, catégorie Account · Essentiels, v3 en ligne, le menu d’envoi de test à côté de Versions, et trois variables déclarées dans l’onglet Variables, dont une marquée Sensible."
   />

5. Ouvrez l’onglet **Variables** et choisissez <UiPath path="transactional.editor.declare" /> pour chaque valeur que
   votre application envoie. Une variable a un type (Texte, Nombre, Oui/non, Date, URL, Liste ou Objet), peut être
   **Obligatoire**, a une **Valeur d’exemple** pour les aperçus, et une valeur par défaut facultative pour le cas où
   elle manque. Marquez une variable comme **Sensible** pour les secrets comme les liens de réinitialisation : elle
   n’est jamais stockée, les journaux et le contenu stocké affichent `••••••`, et le renvoi est désactivé pour ces
   messages. Le panneau vous signale quand une variable du contenu n’est pas déclarée, ou qu’une variable déclarée
   n’est pas utilisée.

6. Ouvrez l’onglet **Données de test** pour enregistrer des jeux nommés de valeurs d’exemple (modifiés en JSON),
   comme « Nouvel utilisateur » et « Sans prénom ». L’aperçu, les contrôles et les rendus de test avant publication
   les utilisent. Utilisez **Prévisualiser avec** au-dessus du canevas pour changer de jeu.

7. Ouvrez l’onglet **Contrôles** pour corriger les problèmes de contenu, d’accessibilité et de liens. Les brouillons
   s’enregistrent automatiquement ; <kbd>⌘</kbd> <kbd>S</kbd> enregistre immédiatement.

8. Choisissez <UiPath path="placement.sendTest > composer.transactional.testSend.menuItem" /> pour recevoir le
   brouillon, tel qu’il est maintenant, dans une boîte de réception. Choisissez l’adresse et, sous
   <UiPath path="composer.transactional.testSend.fillWith" />, un jeu de données de test. Le test passe par la route
   Système avec `[Test]` dans l’objet et n’apparaît jamais dans le
   [journal des messages](/fr/transactional/message-log/). Sans `transactional:send`, les tests ne partent qu’à votre
   propre adresse.

</Steps>

<Aside type="note">
Le suivi des ouvertures et des clics est désactivé par défaut pour les modèles transactionnels. Des liens réécrits
dans une réinitialisation de mot de passe paraissent suspects aux destinataires et aux filtres, et Apple Mail gonfle
les ouvertures. Vous pouvez activer le suivi modèle par modèle.
</Aside>

## Publier une version

Seules les versions publiées partent. Votre application reçoit toujours la version en ligne ; le brouillon n’est
jamais envoyé.

<Steps>

1. Choisissez **Publier** (ou **Publier la v2**, et ainsi de suite) dans la barre supérieure.

2. Lisez **Ce qui change** : les différences d’objet, de texte d’aperçu, de variables et de contenu depuis la version
   en ligne. **Afficher toutes les différences** les montre en entier.

3. Si la modification devait casser les appels de votre application, la boîte de dialogue le signale. ReputeCast
   compare les nouvelles variables obligatoires avec les appels des 7 derniers jours. Par exemple, une nouvelle
   variable obligatoire qu’aucun de ces appels n’a envoyée les ferait échouer avec `missing_variables`. Choisissez
   comment publier :
   - **Rendre la variable facultative, avec une valeur par défaut** (recommandé) : les anciens appels continuent de
     fonctionner et affichent la valeur par défaut jusqu’à ce que votre application envoie la variable.
   - **La garder obligatoire et mettre d’abord à jour l’application** : publiez plus tard, et copiez le nouveau
     payload pour vos développeurs.
   - **Publier quand même** : les appels sans la variable échouent jusqu’à la mise à jour de l’application.

   <Screenshot
     id="transactional-publish"
     alt="La boîte de dialogue de publication de la v2 de « Trial ends in 3 days » : les différences, un avertissement indiquant que 71 appels des 7 derniers jours échoueraient, et l’option recommandée qui rend trial_end_date facultative avec la valeur par défaut soon."
   />

4. Confirmez. La nouvelle version devient ce que rend chaque appel d’API ; la précédente reste dans l’historique.

</Steps>

Si la politique d’approbation de l’espace de travail inclut « La publication d’un modèle transactionnel nécessite
aussi une approbation » (désactivé par défaut), la publication demande d’abord l’accord d’un approbateur ; voir
[exiger une approbation pour les envois à risque](/fr/campaigns/approvals/). Quand la
[politique d’accessibilité](/fr/campaigns/accessibility/) de l’espace de travail est réglée sur Bloquer, les problèmes
d’accessibilité graves bloquent aussi la publication.

## Revenir à une version antérieure

Ouvrez <UiPath path="transactional.editor.versions" />, sélectionnez une version antérieure et choisissez
<UiPath path="transactional.editor.publishAgain" />. Cette version devient ce que rend chaque appel d’API ; les plus
récentes restent dans l’historique, et votre brouillon ne change pas.

## Vérifier le résultat

- L’en-tête affiche la version en ligne, par exemple **v3 en ligne · le brouillon correspond à la v3**.
- Un appel de rendu renvoie le nouvel objet et le nouveau contenu sans rien envoyer ; voir
  [envoyer des e-mails transactionnels avec l’API](/fr/developers/transactional-api/).
- Les nouveaux messages du [journal des messages](/fr/transactional/message-log/) affichent la nouvelle version.

## Dépannage

- **Les appels échouent avec `template_not_published`** → le modèle a un brouillon mais aucune version en ligne.
  Publiez-le.
- **Les appels échouent avec `missing_variables`** → une variable obligatoire manque dans l’appel. Envoyez-la, ou
  rendez la variable facultative avec une valeur par défaut et publiez de nouveau.
- **Le champ ID est en lecture seule** → le modèle a été publié. Dupliquez-le pour utiliser un autre ID.
- **Publier est désactivé avec « Aucune modification depuis la v3 »** → le brouillon correspond à la version en
  ligne ; il n’y a rien de nouveau à publier.
- **L’e-mail de test échoue, car aucun fournisseur n’envoie la route Système** → donnez une route au flux Système
  dans [router les e-mails entre fournisseurs](/fr/providers/routing/).
