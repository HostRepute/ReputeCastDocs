Create transactional email templates in the composer's transactional mode, declare the variables your app sends,
and publish a new version without breaking the calls your app already makes.

## Before you begin

- `transactional:edit` to create templates and save drafts; `transactional:publish` to publish, roll back, archive
  or delete them. Editors can edit; publishing is a [sensitive permission](/reference/permissions/).
- A verified Transactional sender. See [add sending domains and senders](/providers/senders-and-domains/).
- Read [how transactional email works](/transactional/overview/) if categories and the Transactional route are new
  to you.

## Create a template

<Steps>

1. Open <UiPath path="nav.transactional > transactional.common.tabTemplates" /> and choose
   <UiPath path="transactional.common.newTemplate" />. Start from a starter (Password reset, Sign-in link, Email
   verification, Welcome, Receipt or invoice, Trial ending, Team invitation, Usage alert) or from a blank template.
   To bring templates from another platform, use <UiPath path="transactional.common.importTemplates" /> (see
   [import transactional templates](/migrate/transactional-templates/)).

2. In the header, set the name, the **ID** your app calls (such as `password-reset`) and the category. The ID uses
   lowercase letters, digits and single hyphens, up to 64 characters. It is fixed after the first publish; to use
   another ID later, duplicate the template.

3. Write the **Subject** and **Preheader**. Both accept [Liquid](/campaigns/personalization/) tokens such as
   `{{ expires_in }}`. The inbox preview next to them renders with the selected test data.

4. Design the body with the same blocks as the [composer](/campaigns/composer/), plus the ReputeCast blocks
   **Header + logo**, **Receipt lines** and **Transactional footer**. Essential templates get the transactional
   footer with your company and address and no unsubscribe link; Optional categories get the unsubscribe footer.

   <Screenshot
     id="transactional-template"
     alt="The Password reset template in the composer: ID password-reset, category Account · Essential, v3 live, and three declared variables in the Variables tab, one of them marked Sensitive."
   />

5. Open the **Variables** tab and choose <UiPath path="transactional.editor.declare" /> for each value your app
   sends. A variable has a type (Text, Number, Yes/no, Date, URL, List or Object), can be **Required**, has a
   **Sample value** for previews, and an optional default for when it is missing. Mark a variable **Sensitive** for
   secrets such as reset links: it is never stored, logs and stored content show `••••••`, and Resend is off for
   those messages. The panel tells you when a token in the content isn't declared, or a declared variable isn't used.

6. Open the **Test data** tab to save named sets of sample values (edited as JSON), such as "New user" and "No first
   name". The preview, the checks and the test renders before publish use them. Use **Preview with** above the
   canvas to switch sets.

7. Open the **Checks** tab to fix content, accessibility and link issues, and use <UiPath path="composer.sendTest" />
   to send a test to yourself. Drafts autosave; <kbd>⌘</kbd> <kbd>S</kbd> saves at once.

</Steps>

<Aside type="note">
Tracking opens and clicks is off by default for transactional templates. Rewritten links in a password reset look
suspicious to recipients and filters, and Apple Mail inflates opens. You can turn tracking on per template.
</Aside>

## Publish a version

Only published versions send. Your app always gets the live version; the draft never sends.

<Steps>

1. Choose **Publish** (or **Publish v2**, and so on) in the top bar.

2. Read **What changes**: the diff of subject, preheader, variables and content since the live version. **Show the
   full diff** opens all of it.

3. If the change would break your app's calls, the dialog says so. ReputeCast compares the new required variables
   with the calls of the last 7 days. For example, a new required variable that none of those calls sent would make
   them fail with `missing_variables`. Choose how to publish:
   - **Make the variable optional, with a default** (recommended): old calls keep working and print the default
     until your app sends the variable.
   - **Keep it required and update the app first**: publish later, and copy the new payload for your developers.
   - **Publish anyway**: calls without the variable fail until the app is updated.

   <Screenshot
     id="transactional-publish"
     alt="The publish dialog for v2 of Trial ends in 3 days: the diff, a warning that 71 calls in the last 7 days would fail, and the recommended option to make trial_end_date optional with the default soon."
   />

4. Confirm. The new version becomes what every API call renders; the previous one stays in the history.

</Steps>

If the workspace's approval policy includes "Publishing a transactional template also requires approval" (off by default),
publishing asks an approver first; see [require approval for risky sends](/campaigns/approvals/). When the
workspace's [accessibility policy](/campaigns/accessibility/) is set to Block, serious accessibility issues also
block publishing.

## Roll back

Open <UiPath path="transactional.editor.versions" />, pick an earlier version and choose
<UiPath path="transactional.editor.publishAgain" />. That version becomes what every API call renders; the newer
ones stay in the history, and your draft doesn't change.

## Check that it worked

- The header shows the live version, for example **v3 live · draft matches v3**.
- A render call returns the new subject and content without sending; see
  [send transactional email with the API](/developers/transactional-api/).
- New messages in the [message log](/transactional/message-log/) show the new version.

## Troubleshooting

- **Calls fail with `template_not_published`** → the template has a draft but no live version. Publish it.
- **Calls fail with `missing_variables`** → a required variable is missing from the call. Send it, or make the
  variable optional with a default and publish again.
- **The ID field is read-only** → the template was published. Duplicate it to use another ID.
- **Publish is disabled with "No changes since v3"** → the draft matches the live version; there is nothing new to
  publish.
