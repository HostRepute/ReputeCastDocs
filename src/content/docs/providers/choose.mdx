ReputeCast doesn't deliver mail itself: it hands each message to a
[sending provider](/reference/glossary/#sending-provider) you connect, such as Amazon SES, Postmark or your own Postal
server. This page helps you pick an email sending provider for newsletters by comparing what each built-in
[adapter](/reference/glossary/#adapter) can do. You can connect several and split the work between them.

## How the catalog describes a provider

When you open <UiPath path="nav.providers > providers.overview.addProvider" />, the catalog lists every adapter in your
build. Each card shows facts the adapter reports about itself, so the catalog and this page always agree with the code.

<Screenshot
  id="providers-catalog"
  alt="The provider catalog: Help me choose recommends Amazon SES at about $5.00 a month for 50,000 emails, with Resend as the runner-up, above the channel tabs, the filters and cards for Amazon SES, Postmark and Mailgun, each with its bulk-marketing line, price at 50,000 a month and setup time."
/>

- **Bulk marketing** says what the provider's acceptable-use terms allow for bulk mail, with a mark: Allowed, Allowed
  after production access (Amazon SES), Allowed through the Broadcasts API (Resend), Broadcast streams only (Postmark),
  Not allowed · transactional only (Azure Communication Services), Your own policy (your own server) or Depends on the
  server (SMTP).
- **The price at your volume** comes from the adapter's price list in US dollars: a price per 1,000 emails, the monthly
  plan that fits the volume, or "set by your contract", "$0 metered" (your own server) and "set by your server or
  relay". Terms and prices are reviewed quarterly, and they change, so check the provider's own pricing page before you
  decide.
- **Setup** is how long connecting usually takes, honestly: for example 10–15 minutes with an API key, longer for Amazon
  SES off AWS, and about 3 weeks of warm-up on top for a new Postal IP.
- **Details** opens the capability chips: how events come back (webhooks or a bounce mailbox), how the sending domain is
  set up (through the provider's API or by hand), suppression sync, batch sending, dedicated IPs, sandbox handling and
  whether ReputeCast can read your quota. A green chip is supported, an amber chip is supported in part (for example
  "Domain, manual DNS" or "Suppression, pull only"), and a grey, crossed-out chip is not supported.
- **Filters** narrow the list to providers that <UiPath path="connect.catalog.filterBulk" />,
  <UiPath path="connect.catalog.filterWebhooks" /> or offer <UiPath path="connect.catalog.filterDedicated" />.

## Help me choose

At the top of the catalog, <UiPath path="connect.catalog.chooseTitle" /> asks three questions:
<UiPath path="connect.catalog.volumeLabel" /> (you can type `50000`, `50k` or `1.5m`),
<UiPath path="connect.catalog.accountLabel" /> and <UiPath path="connect.catalog.dedicatedLabel" />. Every card then
shows its price at that volume, and the panel names a <UiPath path="connect.catalog.recommended" /> provider with its
monthly price, terms and setup time, and a <UiPath path="connect.catalog.runnerUp" />.

The ranking compares, in order:

1. Bulk-marketing terms: allowed first, then limited (on some streams only, or your own policy). Providers whose terms
   don't allow bulk mail are never recommended.
2. The capabilities ReputeCast uses: event webhooks, domain setup through the API, two-way suppression sync, quota
   discovery and batch sending.
3. The price at your volume, cheapest first; a provider without a price for that volume comes last.

Your own Postal server and SMTP servers or relays are never recommended, because they need a server of your own. With a
dedicated IP, only providers that offer one count. The account you already have doesn't change the ranking; it adds a
note, for example that an existing AWS account may already have SES production access, so there is no 24-hour wait.

Below the built-in providers, the catalog lists the [generic HTTP adapter](/providers/generic-http/) and any
[community adapters](/adapters/overview/) an instance admin installed. Community adapters without a release in the last
year aren't offered for new connections.

## Compare the built-in adapters

<ProviderMatrix family="email" label="Built-in email adapters" />

What each column means:

- **Kind**: API (a hosted provider's HTTP API), Self-hosted (your own Postal mail server), SMTP (any SMTP server or
  relay) or HTTP (any HTTP email API, mapped with the generic HTTP adapter).
- **Bulk marketing**: what the provider's terms allow on the connection. See
  [Bulk-marketing terms](#bulk-marketing-terms) below.
- **Event webhooks**: how the provider reports deliveries, bounces and complaints, and how ReputeCast checks that a
  webhook really came from it. SMTP has no webhooks, so ReputeCast reads bounces from a
  [bounce mailbox](/reference/glossary/#bounce-mailbox) over IMAP or POP3. Read
  [Delivery events and suppression sync](/providers/events-and-sync/).
- **Domain setup**: API means ReputeCast adds your sending domain at the provider and fetches the exact DNS records it
  needs. Postmark needs its account token for this. Manual DNS means ReputeCast shows the records to publish, and you set
  the domain up in the provider's own dashboard.
- **Suppression sync**: Two-way pulls the provider's suppressions into ReputeCast's shared
  [suppression list](/reference/glossary/#suppression-list) and pushes back the hard bounces and complaints that apply to
  all mail, and their removals. Pull only reads the provider's list but can't write to it (Brevo). Local only means the
  provider has no suppression API; ReputeCast checks the shared list before every send instead. Read
  [Delivery events and suppression sync](/providers/events-and-sync/#suppression-sync).
- **Batch size**: how many separately rendered messages go in one API call. Every message is rendered for its recipient
  (tracking links, unsubscribe link, personalization), so providers whose batch calls share one body for all recipients
  (Mailgun, SendGrid, SparkPost, Brevo) get one call per message, with several calls running at a time.
- **Notes**: sandbox handling, quota discovery and anything else that matters when you connect it. Each provider's name
  links to its setup guide.

<Aside type="note">
ReputeCast has no sending service of its own: every message goes through a sending provider you connect.
</Aside>

## Bulk-marketing terms

Newsletters are bulk mail, and some providers only allow it on certain connections. ReputeCast reads each adapter's
policy and uses it in three places:

1. **The catalog and the matrix above** show it as Allowed, Broadcast streams only or Your own policy.
2. **Connecting a provider**: if the terms don't allow bulk mail, the connect wizard doesn't offer the Broadcasts
   [stream](/reference/glossary/#stream) for that provider. For Postmark, bulk mail is allowed on a Broadcast message
   stream, and ReputeCast can create one in your Postmark server for you.
3. **Routing**: if you put a provider whose terms don't allow bulk mail on the Broadcasts route, as a split or as the
   fallback, ReputeCast warns you before it saves and offers a fix: create the Broadcast stream (Postmark), use another
   provider, or save without a fallback. If you keep it anyway, the choice is recorded in the audit log and
   [Send Readiness](/campaigns/send-readiness/) blocks every broadcast until you change the route.

Your own Postal server, an SMTP server or an HTTP API you map yourself show Your own policy: the rules are yours and
those of the network you send from.

## Use several providers

You can connect as many providers as you like and send through several at once. A
[route](/reference/glossary/#route) decides which provider carries each email. Common setups:

- **One provider per kind of mail.** Amazon SES for Broadcasts and Automations, Postmark for System and Transactional
  mail, so a large campaign never slows down a password reset.
- **A fallback for each stream.** If the primary provider goes down, System, Automations and Transactional mail fail over
  to the fallback automatically; Broadcasts wait for your decision unless you choose otherwise. Read
  [Provider health and outages](/providers/health-and-outages/).
- **A weighted split.** Send 90% of Broadcasts through one provider and 10% through a new one while it
  [warms up](/providers/warm-up/), then raise its share.

Read [Route mail across providers](/providers/routing/) to set this up. Bounces and complaints from every provider land
in one suppression list, so an address that bounced at one provider is never tried at another.

## When to choose something else

- Your provider isn't in the catalog but has an HTTP API: map it with the [generic HTTP adapter](/providers/generic-http/)
  without writing code.
- You want a reusable adapter for a provider, or one with logic a mapping can't express: write a
  [community adapter](/adapters/community/).
- You already run a mail server or relay: [send through any SMTP server](/providers/smtp/), or connect your
  [own Postal server](/providers/postal/) through its API to get signed webhooks.
