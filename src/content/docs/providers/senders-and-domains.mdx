When you add sending domain records in <UiPath path="nav.settings > settings.senders" />, ReputeCast fetches the DNS
records each connected sending provider needs for that domain and checks them until they verify. Then you add the
[senders](/reference/glossary/#sender), the From addresses your mail comes from, and choose which one each stream uses
by default, and check the [sending IPs](/reference/glossary/#sending-ip) each provider sends from.

## Before you begin

- You need the `domains:manage` permission. With `providers:view` you can see senders, domains and their records.
- Connect at least one sending provider, so there is someone to fetch records from. Read
  [Connect a sending provider](/providers/connect/). The connect wizard's domain step does the same as this page for the
  provider you are connecting.
- Have access to the domain's DNS records, or a Cloudflare API token if the domain uses Cloudflare.

## Add a sending domain

<Steps>

1. Open <UiPath path="nav.settings > settings.senders" /> and, under <UiPath path="senders.domainsTitle" />, choose
   <UiPath path="senders.addDomain" />.

2. Enter the <UiPath path="senders.domain" /> of your From addresses, for example `news.example.com`, and optionally
   <UiPath path="senders.whatFor" /> ("primary sending domain"). Choose <UiPath path="senders.addDomain" />.

   Every connected provider with a domain API (such as Amazon SES, Mailgun or SendGrid) gets the domain and returns its
   records. For providers without one (such as Postal or an SMTP server), ReputeCast tells you what to set up in the
   provider's own dashboard and which SPF include the domain needs.

3. Open the domain's <UiPath path="senders.records" />. The page lists the records per provider, because each provider
   signs with its own DKIM key: DKIM, the return-path (MAIL FROM) with its SPF record, SPF for the sending domain and
   DMARC. Pick a provider tab to see only its records, or <UiPath path="senders.allProviders" />.

   <Screenshot
     id="settings-sender-domain"
     alt="DNS records for news.acme.io across Amazon SES, Postmark and Postal: 11 of 11 verified, with three DKIM CNAME records, the return-path MX record and SPF for MAIL FROM, and buttons to add all records through the Cloudflare API or copy a zone file."
   />

4. Publish the records at your DNS host. If the nameservers are Cloudflare's,
   <UiPath path="connect.domain.addViaCloudflare" /> adds the missing ones with a token that has Zone › DNS › Edit
   permission; the token is used once and never stored. Otherwise copy each value, or use
   <UiPath path="connect.domain.copyZone" />. Read [Set up SPF, DKIM and DMARC](/deliverability/spf-dkim-dmarc/) for what
   each record does.

5. Watch the status column. While the page is open, ReputeCast checks the records every 30 seconds; each one shows
   Verified, Pending, Missing or "Couldn't check", with the value it found.

6. Optional: under <UiPath path="connect.domain.optionalTitle" />, choose <UiPath path="connect.domain.addTracking" /> to
   use a subdomain such as `go.news.example.com`, with a CNAME to your ReputeCast host, for links and the open pixel. The
   same section shows whether BIMI is set up; read [Set up BIMI](/deliverability/bimi/).

</Steps>

If you connect another provider later, open the domain's records and fetch that provider's records from its tab.

<Aside type="tip">
Give transactional mail a subdomain of its own, such as `notify.example.com`, so its reputation stays apart from your
newsletters. The [transactional setup guide](/transactional/first-send/) marks it as a Transactional domain; only
senders on a Transactional domain can send transactional templates and API mail.
</Aside>

## Add a sender

<Steps>

1. Under <UiPath path="senders.identitiesTitle" />, choose <UiPath path="senders.addSender" />.

2. Fill in the sender:
   - <UiPath path="senders.name" />: shown as the sender in inboxes.
   - <UiPath path="senders.emailAddress" />: its domain must already be one of your sending domains. The address can't
     be changed later.
   - <UiPath path="senders.replyTo" />: where replies go when they shouldn't come back to the From address.
   - <UiPath path="senders.defaultSenderFor" />: the streams (Broadcasts, Automations, System, and Transactional for a
     sender on a Transactional domain) that use this sender unless a campaign or email picks another.
   - <UiPath path="senders.note" />: shown in the list when the sender isn't a stream's default, for example "personal
     sends".
   - <UiPath path="senders.sendsThrough" />: the providers that may send as this address. Clear a provider to mark it
     "Not used" for this sender.

3. Choose <UiPath path="senders.addSender" />. Each provider verifies the sender through the domain's records.

</Steps>

<Screenshot
  id="settings-senders"
  alt="Sender identities of the Acme Newsletter workspace: each From address with its reply-to, the streams it is the default for, and its status at Amazon SES, Postmark and Postal; one sender is Pending on its acme.io DKIM record and shows a Verify button."

The table has a column per connected provider: Verified, Pending (with the record it waits for), Not used or Not set up.
For a pending sender, <UiPath path="senders.verify" /> opens the domain's records for that provider.

## Set the defaults

The <UiPath path="senders.defaultsTitle" /> card at the bottom of the page holds:

- <UiPath path="senders.defaultFrom" />, and the default From for transactional templates (a sender on a Transactional
  domain).
- <UiPath path="senders.replyHandling" />: forward every reply to one address, or use each sender's own reply-to.
  ReputeCast doesn't receive mail, so there is no reply inbox.
- <UiPath path="senders.footerAddress" />: the postal address that email footers show through the `{{ footer_address }}`
  token and that system emails add to their footer. Read
  [Consent and anti-spam law basics](/deliverability/compliance/).
- <UiPath path="senders.trackingDomain" />: a verified tracking domain for links and the open pixel, or the provider
  default (your ReputeCast public URL).

## Check the sending IPs

Each provider card on <UiPath path="nav.providers > providers.tabProviders" /> shows its
<UiPath path="providers.overview.factIps" />: the shared pool, checked at domain level, or its dedicated IPs, checked
one by one. Send Readiness checks each dedicated IP on IP blocklists (an IP the checks haven't reached yet is Unknown),
Deliverability and warm-up read them, and a dedicated IP that never sent for this workspace starts a
[canary phase](/campaigns/live-monitor/) on the next send.

<Screenshot
  id="providers-list"
  alt="Sending providers: the Amazon SES card's sending IPs read the shared pool, checked at domain level, from Amazon SES and checked daily; the Postmark card's sending IPs read the shared pool, with the note that Postmark doesn't report them and an Edit button."
/>

- **Amazon SES, SendGrid, Mailgun, SparkPost and Brevo** report the IPs your account sends from. ReputeCast asks when
  the provider is connected, when its connection step is repeated and every day, and the card says so ("From Amazon
  SES, checked daily"). For Mailgun, only the dedicated IPs assigned to the connection's domain count. If a check
  fails, the card keeps the last answer, says why and offers <UiPath path="providers.overview.checkIpsAgain" />.
- **Other providers** don't report them, and their card says so. With `providers:manage`, choose
  <UiPath path="providers.overview.editIps" />, pick <UiPath path="providers.overview.ipsModeDedicated" /> or
  <UiPath path="providers.overview.ipsModeShared" />, list the dedicated IPs under
  <UiPath path="providers.overview.ipsLabel" /> (one per line, IPv4 or IPv6, up to 64) and choose
  <UiPath path="providers.overview.ipsSave" />. A self-hosted server such as Postal shows "Dedicated · not set yet"
  until you list its IPs.

## Check that it worked

- The domain's row under <UiPath path="senders.domainsTitle" /> shows DKIM, SPF, DMARC and the return-path as verified
  for each provider that uses it.
- Each sender shows Verified for the providers that send as it.
- [Send Readiness](/campaigns/send-readiness/) passes its authentication checks for campaigns from that domain.
  ReputeCast rechecks every domain's DNS every 30 minutes, so a change at your DNS host shows up in Send Readiness
  within the hour.

## Troubleshooting

- **"news.example.com isn't a sending domain of this workspace yet"**: add the domain first, then the sender.
- **A record stays Pending**: the DNS host hasn't published it yet. Some take up to 48 hours. Compare the value found
  with the one shown.
- **A record shows a different value**: an older record with the same name exists, for example a second SPF record.
  A domain must have one SPF record; ReputeCast's value merges the includes you need.
- **"A sender uses this domain. Delete them first."**: a domain can only be deleted when no sender uses it. Deleting it
  stops the checks; the records stay at your DNS host and at each provider until you remove them there.
- **A provider shows Not set up for a sender**: the provider doesn't have the domain yet. Open the domain's records,
  pick the provider's tab and fetch its records.
- **"Couldn't check with …" under a provider's sending IPs**: the provider didn't answer, or the key can't list IPs (for
  Amazon SES, allow `ses:GetDedicatedIps`). The card keeps the IPs it knew; fix the access, then choose
  <UiPath path="providers.overview.checkIpsAgain" />.
