A [bounce](/reference/glossary/#bounce) is a message the receiving mail server refused; a
[complaint](/reference/glossary/#complaint) is a reader marking your email as spam. Both count against the email bounce
rate threshold and complaint limits that sending providers enforce on your account, and against the thresholds
ReputeCast applies while a campaign sends. This page explains how each kind is recorded, which addresses are
suppressed at once, and where those limits sit.

## Hard bounces, soft bounces and complaints

- A [hard bounce](/reference/glossary/#hard-bounce) is a permanent failure: the address doesn't exist, the domain has no
  mail server, or the receiver refused the message for good. SMTP replies for these start with 5 (for example
  `550 5.1.1`).
- A [soft bounce](/reference/glossary/#soft-bounce) is a temporary failure, such as a full mailbox or a receiver that
  asks to try again later. Replies start with 4 (for example `452 4.2.2`). The sending provider retries; a message it
  can't deliver in the end is reported as a soft bounce.
- A [deferral](/reference/glossary/#deferral) is one delayed attempt the sending provider will retry. Many deferrals
  at one mailbox provider usually mean it is throttling your mail. A message counts as deferred once, however many
  attempts were deferred.
- A complaint reaches you through a [feedback loop](/reference/glossary/#feedback-loop): the
  [mailbox provider](/reference/glossary/#mailbox-provider) reports a "Report spam" click to your
  [sending provider](/reference/glossary/#sending-provider), which passes it on.
- A rejected message is one the sending provider refused before sending it, for example because the address is on the
  provider's own suppression list or the content was flagged.

The sending provider decides whether a bounce is hard or soft. ReputeCast keeps that decision, together with the
provider's original event type and code.

## How ReputeCast handles each event

1. The sending provider reports the event to ReputeCast's webhook, or, for an SMTP server, ReputeCast reads it from the
   [bounce mailbox](/reference/glossary/#bounce-mailbox). The raw payload is stored before anything else happens.
2. ReputeCast maps it to one [normalized event](/reference/glossary/#normalized-event) type: `delivered`, `deferred`,
   `hard_bounce`, `soft_bounce`, `complaint`, `rejected`, `open`, `click` or `unsubscribe`. The original type
   ("Bounce · Permanent · General") and code ("550 5.1.1") stay with it.
3. A bounce also gets a [bounce class](/reference/glossary/#bounce-class), read from the enhanced status code and the
   diagnostic text, so the same reply means the same thing at every sending provider.
4. A hard bounce, a complaint and an unsubscribe reported by the provider put the address on the
   [shared suppression list](/reference/glossary/#suppression-list) at once, and the contact's status changes to bounced
   or complained. [Suppression sync](/reference/glossary/#suppression-sync) then pushes the address to every connected
   sending provider that accepts suppressions, so one bounce stops mail everywhere.
5. A block for the sender's reputation or policy (`policy_block`, `spam_block`, `reputation`) never suppresses the
   address, even when the sending provider calls it permanent: the address is valid, and it gets mail again once the
   block is fixed.
6. A soft bounce or a deferral doesn't suppress an address on its own. They count in reports and in the
   [live monitor](/campaigns/live-monitor/). Transactional mail adds one rule: when a Transactional message soft-bounces
   and the address has soft-bounced 3 times within 7 days, the address is suppressed.
7. Bounces by type, deferrals and complaints feed [guarded sending](/reference/glossary/#guarded-sending): when a
   campaign's rates cross the [auto-pause thresholds](#auto-pause-thresholds), ReputeCast slows down or holds the
   affected share.

Copies sent by a [placement test](/deliverability/placement-tests/) to your own seed mailboxes are the one exception:
their bounces and complaints never suppress the seed.

### Bounce classes

Campaign reports group bounces by class in their bounces table, with each sending provider's original codes, and say
what happened to the addresses.

<TableScroll label="Bounce classes">

| Class             | What the receiver said                                    | Row in the report               | What happens                                   |
| ----------------- | --------------------------------------------------------- | ------------------------------- | ---------------------------------------------- |
| `mailbox_unknown` | The address doesn't exist (`5.1.1`, "user unknown")       | Hard · unknown user             | Suppressed automatically                       |
| `domain_invalid`  | The domain doesn't exist or has no mail server            | Hard · domain not found         | Suppressed automatically                       |
| `mailbox_full`    | The mailbox is over quota (`4.2.2`, `5.2.2`)              | Soft · mailbox full             | Retried with the next send                     |
| `temporary`       | A temporary failure that never cleared                    | Soft · deferral expired         | Retried with the next send                     |
| `policy_block`    | Refused by policy, often authentication (`5.7.1`, `5.7.26`) | Blocked · policy or reputation | Never suppressed; investigate and fix the cause |
| `spam_block`      | Refused as spam, or because of a blocklist listing        | Blocked · policy or reputation  | Never suppressed; investigate and fix the cause |
| `reputation`      | Refused or throttled because of sender reputation         | Blocked · policy or reputation  | Never suppressed; investigate and fix the cause |
| `other`           | No code ReputeCast can classify                           | Other                           | You review it                                  |

</TableScroll>

Blocked bounces point at your sending setup, not at the address, so ReputeCast never suppresses them, even when the
sending provider reported them as permanent. In the report's bounces table the blocked row offers
<UiPath path="reports.investigate" />, which shows what each sending provider said, and
<UiPath path="reports.retryTitle" /> drafts the issue again for the blocked addresses still on your list, each once,
to send from Review & send after you fix the cause. Check [SPF, DKIM and DMARC](/deliverability/spf-dkim-dmarc/) and
[blocklist listings](/deliverability/blocklists/), and look the code up in [SMTP error codes](/smtp-errors/).

### Complaints: where they are reported

Most mailbox providers send one report per complaint to your sending provider, which ReputeCast receives as a
`complaint` event: Outlook, Yahoo and many of the providers in Other. Gmail and iCloud never report single complaints.
So ReputeCast counts complaint rates only over mail delivered to mailbox providers that report them, and shows Gmail's
and iCloud's own complaint rates as "n/a" with the reason, never as 0%. Unknown is not zero: a campaign that went only to
Gmail has no complaint rate, not a perfect one. Which mailbox provider a recipient uses comes from the domain's MX
records, so Google Workspace addresses count as Gmail and Microsoft 365 addresses as Outlook.

Gmail works differently: its feedback loop reports aggregate spam rates per identifier in Google
Postmaster Tools, keyed by a `Feedback-ID` header in the message
([Gmail Help, "Feedback Loop"](https://support.google.com/mail/answer/6254652), checked October 2026). ReputeCast adds
that header to Broadcasts, Automations and Transactional mail:

```text title="Feedback-ID header"
Feedback-ID: <campaign, automation or template>:<workspace>:<stream>:reputecast
```

The identifiers group Gmail's data per campaign, per workspace and per stream. With
[HostRepute](/deliverability/hostrepute/) connected, the Postmaster Tools figures, including flagged campaigns, appear
under Deliverability, and the complaint watch after a send can read Gmail's daily spam rate (see
[set the traffic rules](/providers/traffic-rules/)).

Complaints keep arriving for days after delivery. Each one still suppresses the address and counts in the campaign's
report, and for 72 hours after a send (by default) ReputeCast alerts the people who can resume sends when a mailbox provider passes
its complaint limit.

## Sending provider account limits

Sending providers watch your account's bounce and complaint rates and can stop you from sending when they get too
high. Amazon SES, for example, publishes two levels for each rate
([Amazon SES sending review process FAQs](https://docs.aws.amazon.com/ses/latest/dg/faqs-enforcement.html), checked
October 2026):

| Rate           | Account under review | Sending may be paused |
| -------------- | -------------------- | --------------------- |
| Bounce rate    | 5% or more           | 10% or more           |
| Complaint rate | 0.1% or more         | 0.5% or more          |

Amazon SES counts only hard bounces to domains you haven't verified, and complaints only from mailbox providers that
send feedback, measured over a "representative volume" of your mail rather than a fixed period. Its advice is to stay
below 2% bounces and below 0.1% complaints.

ReputeCast stores Amazon SES's two levels with every SES connection and shows each sending provider's bounce and
complaint rate for the last 7 days under [Monitor domain and provider health](/deliverability/health/), next to the
limit it applies to that provider. The complaint rate counts only mail delivered where complaints are reported. The bar
warns from half of the first limit on, once ReputeCast has counted 500 messages in the 7 days. Self-hosted servers
such as Postal or an SMTP server have no account limits; the line shown there is the guard ReputeCast sets, or the
warm-up guard while the server is [warming up](/providers/warm-up/).

## Auto-pause thresholds

ReputeCast's own thresholds apply during each campaign, per mailbox provider and sending provider. They sit at or
below the levels that get an Amazon SES account reviewed, so a bad send stops before it harms the account. Each bounce
type has its own threshold: block/policy bounces per mailbox provider, unknown users over the whole send at two levels
(warn, then pause), and soft bounces and deferrals per mailbox provider over 10 minutes at two levels (slow down, then
pause). Complaints and block/policy bounces clearly over the limit trip a send of any size. Set them in
[traffic rules](/providers/traffic-rules/).

## When to change them

- Keep the defaults while you warm up a new domain or IP, or after a migration: they catch a bad list before a sending
  provider does.
- Raise a threshold for one campaign in [Review & send](/reference/glossary/#review-and-send) only when you know why the rate will be high, for example a
  re-permission campaign to an old list, and send it to a small segment first.
- Lower the bounce threshold if a sending provider's own limit is stricter than ReputeCast's default.

See [Monitor a send and auto-pause](/campaigns/live-monitor/) for what happens when a threshold trips, and
[Workspace sending defaults](/providers/workspace-defaults/) for where the workspace defaults live.
