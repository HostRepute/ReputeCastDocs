ReputeCast runs an email blocklist check on your [sending domains](/reference/glossary/#sending-domain) and
[dedicated IPs](/reference/glossary/#dedicated-ip) once a day, shows the results under
<UiPath path="nav.deliverability > placement.health" />, and turns a listing into a
[Send Readiness](/reference/glossary/#send-readiness) result before your next campaign goes out. This guide shows how to
run the check on demand, read what it found and get a listing removed.

## The lists ReputeCast checks

Without [HostRepute](/reference/glossary/#hostrepute), ReputeCast queries eight public
[blocklists](/reference/glossary/#blocklist) (DNSBLs) itself. IP lists are queried for your dedicated IPs and domain
lists for your sending domains. Mail sent through a sending provider's shared IP pool, such as Amazon SES without
dedicated IPs, is checked at domain level only, because the sending provider manages those IPs.

<TableScroll label="Built-in blocklists">

| List           | Checks  | Impact | Delisting page                                                                   |
| -------------- | ------- | ------ | -------------------------------------------------------------------------------- |
| Spamhaus ZEN   | IPs     | High   | [check.spamhaus.org](https://check.spamhaus.org/)                                |
| Spamhaus DBL   | Domains | High   | [check.spamhaus.org](https://check.spamhaus.org/)                                |
| SURBL          | Domains | High   | [surbl.org](https://surbl.org/surbl-analysis)                                    |
| URIBL          | Domains | High   | [admin.uribl.com](https://admin.uribl.com/)                                      |
| Barracuda BRBL | IPs     | High   | [barracudacentral.org](https://www.barracudacentral.org/rbl/removal-request)     |
| SpamCop        | IPs     | Medium | [spamcop.net](https://www.spamcop.net/bl.shtml)                                  |
| Mailspike      | IPs     | Medium | [mailspike.org](https://mailspike.org/anubis/lookup.html)                        |
| PSBL           | IPs     | Low    | [psbl.org](https://psbl.org/)                                                    |

</TableScroll>

The impact decides what the <UiPath path="review.groupReputation" /> group of Send Readiness does with a listing of the
domain or IPs a campaign sends from: a listing on a high-impact list is a <UiPath path="review.statusBlock" />, a
listing on a medium- or low-impact list is a <UiPath path="review.statusWarn" />. A dedicated IP these checks haven't
reached yet, such as one added since the last daily run, is <UiPath path="review.statusUnknown" /> there until they do:
not checked is never counted as clean.

### Domains looked up live

Some domains are looked up live on Spamhaus DBL and SURBL, over the same DNS resolver, instead of waiting for the daily
check:

- **Link domains.** The composer looks up the domains your email links to as you write, and Send Readiness looks them up
  again on every run. A campaign that links to a listed domain is blocked (see
  [Fix content warnings before sending](/campaigns/content-checks/)).
- **The domains a send rides on that this page doesn't check:** the sending domain's parent domain (`acme.io` for
  `news.acme.io`), the return-path (MAIL FROM) domains of the sending providers carrying the send, and the tracking
  domain of the instance's public URL. Send Readiness looks them up during each run; mailbox providers judge a
  subdomain by its parent domain too, so a listed parent blocks the send.

Answers are kept and shared by every workspace of the instance, so a domain is looked up again only once its answer is
old. A lookup that fails, because DNS didn't answer in time or the lists refused the resolver, is unknown, never clean:
Send Readiness shows it as <UiPath path="review.statusUnknown" /> and looks it up again at the send-time recheck.

When HostRepute is connected, it checks 84 sources every hour instead, and the built-in check is skipped while that
connection is healthy. If HostRepute can't be reached, the built-in check runs as a fallback. See
[Connect HostRepute](/deliverability/hostrepute/).

## Before you begin

- You need `deliverability:view` to open the page and run checks. Owners, Admins, Editors and Viewers have it.
- Connect a [sending provider](/providers/connect/) and [add a sending domain](/providers/senders-and-domains/) first.
  Until then there is nothing to check.
- If you run the server: the instance needs a DNS resolver that blocklists answer. Set it up before you rely on the
  results.

<Aside type="caution" title="Public DNS resolvers get refused">
Spamhaus refuses DNSBL queries that arrive through a public or open resolver such as 1.1.1.1 or 8.8.8.8 and answers
with the error code `127.255.255.254` instead of a listing
([Spamhaus, "Using our public mirrors? Check your return codes now"](https://www.spamhaus.org/resource-hub/dnsbl/using-our-public-mirrors-check-your-return-codes-now/),
checked October 2026). SURBL and URIBL refuse in the same way with `127.0.0.1`. ReputeCast never counts these answers
as listed or clean: the lookup shows as unknown. Point [`dns.servers`](/reference/configuration/#dns) at a recursive
resolver you run yourself.
</Aside>

```yaml title="config.yaml"
dns:
  servers:
    - 10.0.0.53
    - 10.0.0.54:53
```

As an environment variable, separate the servers with commas:

```sh title="Environment"
REPUTECAST_DNS__SERVERS=10.0.0.53,10.0.0.54:53
```

An empty `dns.servers` uses the system's resolvers from `/etc/resolv.conf`. If your host or container forwards DNS to a
public resolver, Spamhaus and URIBL lookups fail even though authentication checks (SPF, DKIM, DMARC) keep working.

## Run a blocklist check

<Steps>

1. Open <UiPath path="nav.deliverability > placement.health" />.

2. Select <UiPath path="deliverability.runChecks" />. When HostRepute is connected, the button reads
   <UiPath path="deliverability.runAll" /> and asks HostRepute to check again as well.

   A progress line shows how many sources have answered. A run started less than a minute after the previous one
   returns that run instead of starting another.

3. When the run finishes, read the blocklists table. Each list shows what it checked, its status
   (<UiPath path="deliverability.listed" /> or <UiPath path="deliverability.clean" />), since when an asset is listed,
   and, for a listing, the list's <UiPath path="deliverability.delistingPage" />.

4. To keep a copy for a ticket or a spreadsheet, select <UiPath path="deliverability.exportReport" />: one CSV row per
   check.

</Steps>

A new listing found by the built-in check also lands in the incident timeline on the same page and in the
notifications of every member who can see Deliverability, with the list's delisting page. A listing on a high-impact
list is marked as serious.

## Get a listing removed

<Steps>

1. Find out why the asset was listed. Open the list's <UiPath path="deliverability.delistingPage" /> and look the
   asset up there. Common causes are mail to old or bought addresses that have turned into
   [spam traps](/reference/glossary/#spam-trap) and a sudden jump in volume from a new IP.

2. Fix the cause before you ask for removal. Remove the addresses that caused it (see
   [Keep your list healthy](/audience/list-health/) and [The suppression list](/audience/suppressions/)), slow down a
   new IP with a [warm-up plan](/providers/warm-up/), and check the sending domain's
   [SPF, DKIM and DMARC records](/deliverability/spf-dkim-dmarc/).

3. Request removal on the list's own page; each list describes its own process there. With HostRepute connected,
   <UiPath path="deliverability.requestDelisting" /> files the request from ReputeCast and HostRepute follows up.

4. If the listed IP belongs to your sending provider rather than to you, contact the sending provider, which controls
   that IP and its sending. Meanwhile, route the affected stream through another provider
   ([Route mail across providers](/providers/routing/)).

5. Run the check again once the list says the listing is gone.

</Steps>

## Check that it worked

- The list shows <UiPath path="deliverability.clean" /> for the asset after the next run.
- The reputation group of Send Readiness passes for the campaign's sending domain, its parent, return-path and tracking
  domains, and its dedicated IPs ([Send Readiness: check before you send](/campaigns/send-readiness/)).

## Troubleshooting

- **The run says some lookups didn't answer.** Those lookups show as unknown, not clean. The usual cause is a public
  DNS resolver: set `dns.servers` as shown in [Before you begin](#before-you-begin). Slow resolvers can also time out;
  the per-lookup timeout is `dns.timeout` (default 4 s).
- **Send Readiness says a domain couldn't be checked on Spamhaus DBL and SURBL.** The live lookup didn't answer or was
  refused. Same fix: your own resolver. Then select <UiPath path="review.rerun" /> on Review & send.
- **Send Readiness says a dedicated IP isn't checked on IP blocklists yet.** The IP is new to these checks. Select
  <UiPath path="deliverability.runChecks" /> here, then run Send Readiness again.
- **Spamhaus ZEN or DBL never shows up in the table.** Spamhaus refused every query, so no result was stored. Same fix:
  your own resolver.
- **The button does nothing new.** A run already in progress, or one started less than a minute ago, is shown instead
  of a new one. Wait for it to finish.
- **"Connect a sending provider first" appears.** No sending domain or dedicated IP exists yet. Finish
  [connecting a sending provider](/providers/connect/).
- **A shared-pool IP is listed elsewhere.** ReputeCast doesn't check shared IPs; your sending provider monitors them.
  Ask the sending provider, or move the stream to a provider with a clean pool.
- **The listing comes back after removal.** The cause is still there. Look at bounces and complaints by mailbox
  provider in your [campaign reports](/campaigns/reports/) and stop mailing contacts who never engage.
