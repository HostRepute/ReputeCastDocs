An inbox placement test sends one copy of an email to each [seed mailbox](/reference/glossary/#seed-mailbox) you own,
then signs in to those mailboxes and reports where each copy landed: the inbox, a tab such as Promotions, the spam
folder, or nowhere, counted per mailbox provider. Use it to compare emails and sending providers before a campaign goes
to your list. Tests run when someone starts one, or when a send's [canary](/reference/glossary/#canary) includes the seed
mailboxes; nothing runs on a schedule.

## Before you begin

- Adding, reconnecting and removing seed mailboxes needs `placement:manage`, a sensitive permission, because a seed's
  password or token can read the whole mailbox. Running a test needs `placement:run`. Only people can start tests and
  manage seeds: API keys can read test results, and AI agents can hold neither permission.
- Use mailboxes that exist only for tests. ReputeCast looks only for messages that carry a test token and opens only
  the inbox, the spam folder and Gmail's tabs, but the credentials give access to everything in the mailbox.
- The content you test needs a verified sender on the stream it uses ([Add sending domains and senders](/providers/senders-and-domains/)).
- To connect Gmail, Google Workspace, Outlook.com or Microsoft 365 seeds with OAuth, an
  [instance admin](/reference/glossary/#instance-admin) first adds a redirect URI to the instance's sign-in apps (see
  [Set up the sign-in apps for OAuth seeds](#set-up-the-sign-in-apps-for-oauth-seeds)).

## How each seed connects

| Mailbox provider           | Connect with                                    | Notes                                                                                                   |
| -------------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Gmail                      | IMAP app password (recommended) or OAuth        | Tabs (Primary, Promotions, Updates, Social, Forums) are read from Gmail's labels.                      |
| Google Workspace           | OAuth or IMAP app password                      | OAuth through an app of the same Workspace organization avoids Google's limits on unverified apps.     |
| Outlook.com, Microsoft 365 | OAuth                                           | Read through Microsoft Graph, which tells Focused from Other. Microsoft refuses passwords over IMAP.   |
| Yahoo, AOL                 | IMAP app password                               | Created in the account's security settings.                                                             |
| iCloud                     | App-specific password                           | The Apple ID needs two-factor authentication.                                                           |
| GMX, Web.de                | The account password, with IMAP turned on       | Turn on IMAP in the mailbox's settings first.                                                           |

ReputeCast fills in the IMAP server and port for every provider. Passwords and tokens are sealed with the instance's
secret key and are write-only: the API never returns them.

Microsoft turned off basic authentication, app passwords included, for IMAP in Exchange Online
([Microsoft Learn, "Deprecation of Basic authentication in Exchange Online"](https://learn.microsoft.com/en-us/exchange/clients-and-mobile-in-exchange-online/deprecation-of-basic-authentication-exchange-online),
checked October 2026), and ReputeCast's add dialog refuses an app password for Outlook.com and Microsoft 365 seeds.

## Set up the sign-in apps for OAuth seeds

OAuth seeds reuse the instance's Google and Microsoft sign-in apps from
<UiPath path="shell.userMenuInstanceAdmin > admin.authentication" />; there is no separate app to register. Each app
needs a second redirect URI next to the sign-in one:

```text title="Redirect URI for seed mailboxes"
<public URL>/api/v1/placement/oauth/callback
```

<Steps>

1. In the Google app, add the redirect URI above and the scope `https://mail.google.com/` to its consent screen. IMAP
   access with OAuth needs that scope.

2. In the Microsoft app, add the redirect URI and the delegated Microsoft Graph permission `Mail.ReadWrite` (with
   `offline_access`). Allow personal Microsoft accounts as well as work accounts, or Outlook.com seeds can't sign in.

3. Set up the apps themselves as described in [Google, Microsoft and GitHub sign-in](/self-hosting/social-sign-in/).

</Steps>

<Aside type="note" title="Google's limits on unverified apps">
`https://mail.google.com/` is a restricted scope. While a Google app's consent screen has an external user type and the
publishing status "Testing", Google issues refresh tokens that expire after 7 days
([Google, "Using OAuth 2.0 to access Google APIs"](https://developers.google.com/identity/protocols/oauth2), checked
October 2026), so such a seed shows as signed out every week. Connect gmail.com seeds with an app password instead.
Apps used only inside one Google Workspace organization (user type Internal) need no verification
([Google Cloud Help, "Unverified apps"](https://support.google.com/cloud/answer/7454865), checked October 2026), so a
Google Workspace seed in that organization can use OAuth without these limits.
</Aside>

## Add seed mailboxes

<Steps>

1. Open <UiPath path="nav.deliverability > placement.placementTests" /> and select
   <UiPath path="placement.pillSeeds" />.

2. Select <UiPath path="placement.addSeed" /> and pick the mailbox provider.

3. Under <UiPath path="placement.connectWith" />, choose <UiPath path="placement.viaImap" /> or
   <UiPath path="placement.viaOAuth" /> where the provider offers both.

   - **App password:** enter the address and the password, then select <UiPath path="placement.checkAndAdd" />.
     ReputeCast signs in and lists the folders it found, such as the inbox, the tabs and the spam folder.
   - **OAuth:** sign in to the seed mailbox at Google or Microsoft and allow ReputeCast to read and change its mail.
     Finish within 10 minutes; the browser then returns to ReputeCast and the seed is added.

4. Add a seed at each mailbox provider your readers use. A test can send to up to 100 seeds.

</Steps>

## Run a placement test

<Steps>

1. Select <UiPath path="placement.runTest" />. You can also start a test from the campaign's
   [Review & send](#test-from-review--send), from the composer's <UiPath path="placement.sendTest" /> menu or from the
   warm-up planner.

2. Pick what to test: a campaign, a campaign template, a digest's next issue or a transactional template. Choose the
   version when the email has A/B variants, language versions or conditional content.

3. Choose how the copies go out:

   - With <UiPath path="placement.throughRouteTitle" />, each seed gets the sending provider the route would pick for
     it.
   - With <UiPath path="placement.throughOneTitle" />, you test one sending provider on its own.
   - With <UiPath path="placement.throughCompareTitle" />, each seed gets one copy per provider, 2 minutes apart,
     alternating which provider goes first. You can compare up to 6 providers.

4. Pick the sender and the seeds (all connected seeds, or some). The dialog shows the number of copies, their cost and,
   for a provider that is warming up, how many of today's warm-up cap they use.

5. Select <UiPath path="placement.startTest" />.

</Steps>

Copies are real sends with the same headers and link tracking as the campaign. Their opens and clicks are never
counted, they never appear in reports or contact timelines, and bounces or complaints from a seed never suppress it. A
test never changes a send or its [Send Readiness](/reference/glossary/#send-readiness) verdict.

## Test from Review & send

A campaign's [Review & send](/reference/glossary/#review-and-send) page has a <UiPath path="placement.entryTitle" />
card next to the checks. It is optional and never changes the [Send Readiness](/campaigns/send-readiness/) verdict.

- The card says how many seed mailboxes a test reaches and at which mailbox providers, how many need attention (their
  sign-in failed or expired, so tests skip them), and that a test takes about 3 minutes.
- <UiPath path="placement.runTest" /> opens the test dialog set to this campaign as scheduled: through the route, or
  comparing the sending providers when the route uses more than one. Running a test needs `placement:run`; without it,
  the button names who can.
- The campaign's latest result shows one line per mailbox provider, counting Inbox, the provider's own tab for bulk mail
  (Promotions at Gmail, Other at Outlook.com) and Spam, for example "Gmail · Inbox 2 · Promotions 2 · Spam 0", with a
  bar. When the route compared providers, a line per sending provider follows, such as "Through SES: Inbox 8 · Tab 2".
  <UiPath path="placement.entryViewResults" /> opens the full result.

## Seed placement during a canary

When a send starts with a canary and the canary includes seed mailboxes, ReputeCast starts a placement test of the
campaign through its route to every connected seed, as one from Review & send. The canary's seed placement gate on the
[live monitor](/campaigns/live-monitor/) reads it per mailbox provider, so copies landing in spam can hold the send
before everyone gets it. The test appears in the tests list like any other.

- The headline counts seeds, for example "8 of 10 seeds in the inbox", never a percentage: a handful of seeds is a
  sample, not your audience.
- Each cell shows where the copy landed in the provider's own words (Inbox, a tab, the spam folder), the time it took
  to arrive, and the SPF, DKIM and DMARC results the receiving server wrote into the copy's headers. Open a copy to read
  its headers and the sending provider's events.
- Copies in the seeds are deleted 24 hours after each test by default. Change that under
  <UiPath path="placement.deletionSettings" /> (24 hours after each test, when the test finishes, or never; needs
  `placement:manage`), or remove one test's copies with <UiPath path="placement.deleteCopiesNow" />.

## Check that it worked

- The test's status is <UiPath path="placement.statusFinished" /> and every seed has a result.
- Each seed on <UiPath path="placement.pillSeeds" /> shows <UiPath path="placement.seedConnected" /> and when it was
  last used.

## Troubleshooting

- **A seed shows <UiPath path="placement.seedFailed" />.** The mailbox provider rejected the app password, often
  because it was revoked or the account's password changed. Tests skip the seed until you select
  <UiPath path="placement.reconnect" /> and paste a new app password.
- **A seed shows <UiPath path="placement.seedExpired" />.** The mailbox provider ended ReputeCast's OAuth access. A
  gmail.com seed connected through an app in Testing status expires every 7 days; reconnect it with an app password.
- **OAuth says the Google or Microsoft sign-in isn't set up.** The instance's sign-in app has no client ID and secret
  yet. An instance admin adds them in <UiPath path="shell.userMenuInstanceAdmin > admin.authentication" />; until then,
  connect Gmail and Google Workspace seeds with an app password.
- **Outlook.com refuses the app password.** Expected: connect Outlook.com and Microsoft 365 seeds with OAuth.
- **The test can't start.** The dialog lists why: no connected seed, no verified sender for the stream on a picked
  provider, a provider that is down, or a warm-up cap that the copies would exceed.
- **Copies land in spam at one mailbox provider.** Check the authentication results in the copy's headers, then
  [SPF, DKIM and DMARC](/deliverability/spf-dkim-dmarc/) and [blocklist listings](/deliverability/blocklists/) for the
  sending domain.
